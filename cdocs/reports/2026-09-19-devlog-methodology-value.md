# Devlog Methodology: Value or Waste

> BLUF(sonnet/devlog-methodology-eval): Keep it, mostly as-is, for one reason the field independently converges on: hand-authored structured notes beat both raw transcripts and cheap post-hoc summaries at the one job that matters, letting a *different* agent resume the work cold.
> The methodology is not "CoT in triplicate": the devlog is not a re-summary of the chat, it is a decision record with citations and pasted verification evidence that never existed in prose form until written.
> The one real waste is the automatic compaction re-summary layer riding on top of a well-kept devlog: if the devlog is current, per-session compaction should point back at it rather than re-derive a second lossy summary of the same ground.
> Token cost is a rounding error next to code-reading/code-review tokens; the real cost is human/agent *reading* time on oversized devlogs (this repo's own 13-46KB "iterate" logs), not authoring tokens.

## Context / Background

This repo's `CLAUDE.md` and `.claude/rules/cdocs.md` mandate a devlog (`cdocs/devlogs/YYYY-MM-DD-name.md`) for all substantive work, positioned as: a decision record (why, not just what), an issue/fix log, a verification-evidence ledger (no completion claims without pasted output), and the substrate for the orchestration-discipline "handoff-before-compact" pattern (`orchestration-discipline.md` Pillar 2), which claims a hand-written handoff is "more complete" than auto-compaction's lossy summary because it is written *before* compaction rather than *by* it.
This report asks: is that actually true, is it worth the tokens, and are there cheaper or better alternatives (archiving the raw chat transcript; a small model distilling the devlog post-hoc from the transcript)?

## What We Actually Do (grounded in the files)

Read directly, not inferred:
- `.claude/rules/cdocs.md` "Devlog Convention": mandatory, "single source of truth," updated as-you-go not at the end.
- `plugins/cdocs/skills/devlog/SKILL.md` and its `template.md`: prescribed sections are Objective, Plan, Testing Approach, Implementation Notes, Debugging Process (4-phase), Changes Made (file table), Verification (pasted build/test/runtime evidence, explicitly "no completion claims without pasted evidence"), Screenshots, Documentation Updated.
- `cdocs/devlogs/README.md`: same core sections, one paragraph, pointing at the skill for detail.
- `orchestration-discipline.md` Pillar 2: the devlog is also where the overseer's Completed/Decisions-Made/Open-Todos handoff lives, written *before* `/compact`, on the claim that a hand-written handoff beats auto-compaction's summary because compaction is inherently lossy and a human/agent curator applies judgment a summarizer model does not have.

Sampled real devlogs to see what actually gets written (not the aspirational template):
- `cdocs/devlogs/2026-09-18-owner-mount-authz.md` (159 lines): a single file spanning a proposal, a round-1 and round-2 review's blocking findings and how each was folded in, an implementation with file:line citations for every claim, a baseline-RED/fixed-GREEN discriminator run, and four explicitly-labeled "Deviations / honest gaps." This is not a transcript-of-the-conversation; it is closer to a structured commit message plus a decision log plus a test report, none of which existed as prose anywhere else in the session.
- `cdocs/devlogs/2026-09-18-owner-mount-authz-dogfood-bringup.md` (69 lines): a bring-up log with three independently-verified signals (WebSocket frame probe, app's own error-console signal, server-side persisted-file evidence) for a single claim ("owner is no longer denied"). Dense, falsifiable, and shorter than the conversation that produced it would have been.
- `cdocs/devlogs/2026-09-18-crdt-pseudo-conflicts-report.md` (41 lines): explicitly separates "what this report is NOT" (not an empirical spike) as a load-bearing caveat, and records which of two parallel research agents found what, which a raw transcript would bury under tool-call noise.
- Contrast: `cdocs/devlogs/2026-09-17-loro-repo-identity-acl-wiring-impl.md` (45KB) and the paired `-iterate.md` (36KB) are the outsized end of the distribution: these read as append-only logs across 8 iterations rather than curated summaries, and are the closest this repo gets to the "chat transcript with the tool noise stripped" failure mode called out in Step 2 below.

Net: at the well-behaved end of the sample, devlogs are dense, citation-heavy, decision-focused artifacts that are *shorter* and *more useful for resumption* than the underlying transcript would be. At the long-running-iterate-loop end, they visibly drift toward append-only chronologies that a fresh reader would struggle to skim in 30 seconds, which is exactly the failure the orchestration-discipline "30-second orientation" bar is meant to prevent and, on the evidence of file size, does not always achieve.

## What the Field Does

**Structured memory over raw logs is the converged position, not a contrarian one.** Anthropic's own context-engineering guidance for Claude models frames memory as "structured note-taking: the agent writes to persistent external storage so it can track progress across tasks and sessions without keeping everything in active context," explicitly contrasted with keeping conversation history in context, and demonstrates it cutting a follow-on session's file re-reads from 8 to 4 and peak context from ~334K to ~173K tokens. [Context engineering: memory, compaction, and tool clearing: Claude Cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools)

**"Save the transcript and grep it later" is a named anti-pattern.** Alex Op's survey of Claude Code memory patterns states it flatly: "The naive version is to save every conversation transcript and grep it later. That technically counts, but it's useless," and instead documents the pattern this repo follows almost exactly: task-scoped progress files (Peter Steinberger's `/tmp/refactor-{project}.md`, Geoffrey Huntley's Ralph-loop `fix_plan.md`/`AGENT.md`) as the actual working memory, with distilled notes replacing full transcripts because "compression and intentionality matter for usefulness." [The Four Types of Memory for AI Agents: alexop.dev](https://alexop.dev/posts/four-types-memory-coding-agents-claude-code/)

**Production evidence favors curated, merged summaries over both verbatim history and fresh re-summarization.** Factory.ai's evaluation across 36,000 real engineering-session messages found that *anchored iterative summarization* (merging each newly-compressed span into a persistent, section-structured summary: intent, file changes, decisions, next steps) scored higher on resumption quality than both keeping verbatim history and re-summarizing from scratch each time, and scored above both Anthropic's and OpenAI's default compaction approaches on their probe suite (3.70 vs. 3.44 vs. 3.35). [Why AI agents forget mid-task (and how to fix it): Wire Blog](https://usewire.io/blog/why-ai-agents-forget-mid-task/), [Designing Context Compression for Production Agents: akjamie.github.io](https://akjamie.github.io/post/2026-05-24-context-compressor-deep-dive/)

**Coding-agent frameworks converge on the same shape.** OpenHands' `LLMSummarizingCondenser` explicitly preserves "user goals, technical specifications, and critical files" while discarding raw turn-by-turn history once it ages out, the same why-not-just-what selection this repo's devlog template enforces via its Implementation Notes / Changes Made split. [Context Condenser: OpenHands Docs](https://docs.openhands.dev/sdk/guides/context-condenser)

**Academic work on agent handoff is nascent but points the same direction.** A 2026 paper on "handoff debt," the rediscovery cost an agent pays taking over an interrupted task, compares structured handoff notes, raw transcripts, and no documentation, and reports that structured documentation "significantly reduces rediscovery time" versus either alternative (the paper's abstract-level claim; full quantitative tables were not extractable from the fetched PDF). [Handoff Debt: The Rediscovery Cost When Coding Agents Take Over Interrupted Tasks (arXiv:2606.02875)](https://arxiv.org/pdf/2606.02875). A companion paper proposes a dual-layer architecture (immutable event log plus curated summary) explicitly because neither layer alone is sufficient: raw logs preserve fidelity but create "cognitive overhead," curated notes compress but "risk losing nuance." [ESAA-Conversational: An Event-Sourced Memory Layer for LLM Coding Agent Handoff (arXiv:2606.23752)](https://arxiv.org/pdf/2606.23752)

## The "CoT in Triplicate" Question, Answered

The premise (chat narration -> devlog re-summary -> compaction re-summary is triple redundant) is **half right**, and the half that's right identifies a real, fixable waste in this repo's own setup, not in devlogs generally.

- **Chat narration -> devlog is not redundant summarization, it's a different artifact.** The sampled devlogs above are not condensed retellings of the conversation; they contain content that never existed as conversational prose at all: file:line citations gathered across many tool calls, a table of "what a legacy owner-spare bug would have caused," pasted `Tests 165 passed (165)` output, and an explicit "what this report is NOT" caveat. A transcript replay could not reconstruct these without re-deriving them, because the devlog is where the *synthesis* happens, not where a synthesis that already exists gets copied. This matches the field's converged shape above: structured memory is not a compressed transcript, it is a purpose-built decision record built by an agent that has (uniquely) full context at authoring time.
- **Devlog -> compaction summary is the genuinely redundant hop.** If a devlog is kept current (per this repo's own "update as you go" rule), auto-compaction re-summarizing the same working session is re-deriving a second, lossier synthesis of ground the devlog already covers, using a summarizer that (per Anthropic's own compaction probes) drops obscure-but-load-bearing details the human/agent author would have kept. [Claude Cookbook, "What survived in testing" example above.] The fix is not "stop writing devlogs," it is "point compaction at the devlog": the orchestration-discipline handoff-before-compact pattern already gestures at this ("a hand-written handoff is more complete than auto-compaction's lossy summary") but this repo does not currently instruct compaction to *read* the devlog it just wrote before summarizing, so the two artifacts are produced independently rather than one subsuming the other.
- **Net verdict:** two layers (chat -> curated devlog), not three. The third layer (compaction) should degrade to "restore from devlog" when a current one exists, per the field's own dual-layer-not-triple-layer pattern (event log + curated summary, never three tiers).

## Alternatives Evaluated

### Raw-transcript archive (instead of authoring a devlog)
Rejected as a *replacement*, useful as a *supplement*. The transcript has complete fidelity but near-zero signal-to-noise: tool-call scaffolding, false starts, and re-reads dominate it, and nothing in it is pre-marked as a decision, a verification result, or a caveat. The field explicitly names this the naive/useless baseline. [alexop.dev, above.] This repo's own 45KB `-impl.md`/`-iterate.md` logs are the warning sign for what a devlog looks like when it drifts toward transcript-shaped (append-everything) rather than decision-shaped: long, but not more resumable for it. A cheap, non-replacing use of the raw transcript: retain it (Claude Code already does, as session history) purely as a fallback citation source when a devlog claim needs re-verification, never as the primary artifact.

### Cheap post-hoc distillation (small/open model writes the devlog after the fact from the transcript)
Attractive on cost, weak on content. Two problems, both reasoning-shaped rather than compression-shaped:
1. **The valuable content isn't in the transcript to extract.** Much of what makes the sampled devlogs useful, the file:line citations gathered by *reading source*, the discriminator design, the explicit "here's what I did NOT verify," reflects judgment applied during the work, not facts stated in chat. A post-hoc summarizer without that access can only compress what was said, not add what should have been checked. This is the same gap the field's compaction probes surface: a generic summarizer keeps high-salience facts and drops "obscure but load-bearing" specifics, because it cannot tell which specifics will matter later. [Claude Cookbook probe result above: 0/3 obscure specifics survived a generic compaction pass.]
2. **A small model distilling a large agent's technical transcript is a capability mismatch**, not merely a cost-saving substitution: identifying which of dozens of file reads produced the load-bearing citation requires the same domain reasoning that produced the citation in the first place.
Where this genuinely helps: **frontmatter and mechanical hygiene**, which this repo already delegates to a cheap tier (`cdocs:nit-fix` on haiku, `cdocs:triage` on sonnet per `model-tiering.md`). That is post-hoc distillation correctly scoped to mechanical, not judgment-bearing, work.

### Hybrid (what the evidence actually supports)
Author the devlog as-you-go (current practice, keep), let it absorb the handoff-before-compact role explicitly rather than in parallel with a separate compaction summary (fix), and treat the raw transcript as a passive fallback never a primary artifact (already true in practice, worth stating explicitly). This is exactly Factory's and ESAA-Conversational's converged shape: one durable curated layer, one raw fallback layer, no independent third summarization pass.

## Token-Cost Reality Check

Devlog authoring tokens are not the dominant cost in a coding session, and the mandate is not measurably wasteful on cost grounds alone. A 30-task GPT-5-reasoning study of agentic software-engineering sessions found Code Review dominates spend at 59.4% of total tokens (Code Completion + Code Review together over 86%), with Design at 2.4% and Coding at 8.6%; documentation-phase tokens were not broken out as a comparable top-line percentage, but were characterized as strongly input-heavy (80.2% input vs. output), i.e. dominated by the cost of *reading* context to write the entry, not by the entry's own prose. [RDEL #138: Where do all the tokens go in agentic software engineering?](https://rdel.substack.com/p/rdel-138-where-do-all-the-tokens) A broader analysis of 722 agentic sessions (34.56B tokens) found only 12.2% of total spend was newly-generated output text of any kind, coding included; the overwhelming majority is re-sent context on every turn. [AI Coding Cost Analysis: Augment Code](https://www.augmentcode.com/guides/ai-coding-cost-analysis-agent-token-spend)

Applied to this repo: a 159-line devlog like `owner-mount-authz.md` is roughly 1-2K output tokens against a workstream that read dozens of source files, ran multiple test suites, and dispatched review rounds, each of which independently costs far more in input tokens than the devlog's own prose. **The real cost this methodology imposes is not authoring tokens, it's downstream reading cost and human/agent skim time on the outsized devlogs** (the 45KB `-impl.md`/`-iterate.md` files observed in this repo's own `cdocs/devlogs/`), which run counter to the "30-second orientation" bar the discipline itself sets and are the concrete artifact of the failure mode this report otherwise argues against.

## Recommendations

1. **Keep the mandatory devlog for substantive work.** The sampled evidence (dense, citation-bearing, verification-anchored) and the field's converged position (structured curated memory beats both raw transcript and generic post-hoc summarization) both support it. This is not a defensible-status-quo conclusion reached by default: the alternatives were evaluated on their merits and lose on the specific job (a different agent, cold, resuming the work) this methodology is built for.
2. **Collapse the third summarization layer.** Change the compaction-before-checkpoint step (`orchestration-discipline.md` Pillar 2) from "write a handoff, then let auto-compaction independently re-summarize" to "write/update the devlog, then let compaction cite or restore from it" wherever the harness allows steering the compaction prompt (per the Claude Cookbook `compact_20260112` `instructions` field). Where it does not, the handoff section should say explicitly that it *is* the compaction input, not a parallel artifact.
3. **Cap devlog size or split by phase.** The 13-46KB `-impl.md`/`-iterate.md`/`-propose.md` files are the observed failure mode: past roughly 10-15KB, a devlog stops being skimmable and starts being an append-only chronology, i.e. exactly the raw-transcript shape this methodology exists to avoid. Concrete fix: when an `/iterate` loop crosses ~5 rounds, checkpoint into a fresh dated devlog (as this repo already does for some multi-day workstreams, e.g. `-propose.md` / `-iterate.md` / `-impl.md` splits) rather than appending indefinitely to one file, and require each split's opening BLUF to stand alone.
4. **Do not build a cheap-model post-hoc distillation pipeline** for devlogs themselves; the content that makes them valuable is produced by reasoning during the work, not extractable from a transcript after the fact. Continue scoping cheap-tier models to what they already do well here: mechanical frontmatter/convention fixes (`nit-fix`, `triage`), not judgment-bearing synthesis.
5. **Retain the raw session transcript as a passive fallback only**, for the rare case a devlog's claim needs re-verification against exactly what was said or done; never promote it to the primary artifact of record.
