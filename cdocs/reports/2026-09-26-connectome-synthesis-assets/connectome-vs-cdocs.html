Research synthesis · cdocs/connectome-research · 2026-09-26

One agent for a lifetime.
Many agents for one project.

Anima Labs' Connectome and cdocs look like rival memory systems. They mostly solve different problems, and they meet in one place: a long-lived specialist that stays on a single project. This page lays out Connectome's architecture, where the two overlap, the case for and against agent identity, and what cdocs should borrow.

Do not adopt

  • Connectome as a runtime (pre-1.0, fast-moving, unclear licensing).
  • Self-voiced, as-of summaries as a recall channel for coding.
  • Model-bound continuity.

Adopt, in order

  • 1a. Human-reviewed distill pass; 1b. supersedes links.
  • 2. A generated live index, read on demand, never pinned.
  • 3. Links from devlogs to the session transcripts Claude Code already writes.

Test, do not assume

  • Agent identity is unmeasured, not refuted. Run a two-arm experiment against current handoffs: cited per-role notes, and notes plus a first-person self-model.

Connectome · provenance

Five libraries for agents that keep going

Anima Labs, a San Francisco 501(c)(3) founded in 2025 by Janus and Antra Tessera, describes Connectome as "open-source infrastructure for AI agents that continue over time." Its core claim, from the design doc: "The archive is monotonic; the live view is a projection." Every event is kept. Each turn, a fresh context is compiled from that archive.

The name has history. An earlier Python-era antra-tess/connectome and a VEIL-based connectome-ts are both superseded and no longer public. Chronicle's own design doc is titled "Loom of Looms". inference The branchable record is the loom idea, from the lineage of Janus's loom work, moved into agent infrastructure.

Connectome · tier 1 of 4

A lossless archive you can branch

Chronicle stores records. Each record has an id, a per-branch sequence, a type, a payload, and two link lists: caused_by and linked_to. Branches are copy-on-write forks with a parent and a branch point. Named state slots (the message log, the summary tree, fold resolutions, the workspace filesystem) are materialized from records on the active branch.

Branching is how the agent's history gets revised. /undo and /restore create branches. /checkpoint creates no branch; it records a position that /restore can branch from later. Anima's site adds the caveat: branching changes the recorded trajectory, and actions already taken in the outside world still have their consequences.

Connectome · tiers 3 and 4

The context is compiled every turn

The context manager splits history into chunks of about 3–6k tokens. The agent's own model (or a configured compressionModel) writes a first-person L1 recollection of each chunk. About six L1s merge into an L2, and so on, with no fixed number of levels. The mint request holds only what came before the chunk, so a memory never knows how things turned out.

Writing summaries and showing them are separate steps. Summaries are written once, in the background. Each turn, a fold solver picks a resolution for each stretch of the middle, then renders it as a recall pair: a "Context Manager" participant asks what the agent remembers, and the agent's own voice answers. The head and the recent tail stay verbatim. Because Anthropic's prompt cache matches exact prefixes, the solver prefers to keep last turn's layout, and it folds deep history first.

Solver facts. The library default is flat-profile. The onboarding runbook describes the deployed stack as kv-stable, with flat-profile as the fallback. The newest kv-unified solver (rev 6) takes 1.7–1.9 s per compile at about 260k tokens, after a fix that removed a roughly 10× slowdown. That figure applies to kv-unified only. Which solver each production resident runs is unverified.

Connectome · background

Summaries are written by a clock, not by turns

A turn does not summarize anything. When messages are appended, newly closed chunks are queued (the newest chunk is held back). A separate framework timer drains the queues. Compile never waits for pending compression, so a new L1 appears at the first compile after its mint finishes. With the 5 s default that is usually the next turn, but nothing guarantees it.

Connectome · identity

Three kinds of identity, kept apart

Narrative identity comes from what is in context: the recipe's system prompt, the verbatim head ("origin/anchor"), and the chain of self-voiced memories. The mint path refuses to add a summarizer system header because, per a code comment, it would be "an alternative identity source that competes with the structural one." Operator doctrine binds each agent to one model: "feeding one model's chronicle to another is treated as a continuity violation." That rule belongs to the operators. The memory layer does not enforce it, since compressionModel can be set separately from the speaking model.

cdocs · the other system

A shared, typed record of why the project is the way it is

cdocs keeps memory as markdown in the project's git repo: devlogs, proposals, reviews, and reports, each with fixed frontmatter. Agents write nearly all of it. Human steering causes documents to exist but is never recorded as authorship. Nothing loads by default except the rules layer. Everything else is pulled when an agent decides to read it, and the retriever is the agent itself running grep and glob.

The core contrast

Two problems that meet at a long-lived specialist

Connectome's unit of continuity is an agent. It answers: what should this agent see this turn, given everything it has lived? cdocs' unit is a project. It answers: what does any future agent or human need to know about why the project is the way it is? The two converge for a long-lived specialist working a single project, such as a persistent reviewer. cdocs' nearest mechanism, the Pillar 3 durable specialist, lasts for one workstream and is then disposed of.

The overlap has tiers. There is one functional equivalence, three partial analogues, and one convergent practice. Each system also has a core the other lacks.

Equivalence. Connectome's guide calls the workspace "your durable, verbatim memory" for anything that "must stay exact." The cdocs corpus is that channel made shared, typed, and committed. Partial analogues. A devlog handoff (Completed / Decisions / Open Todos) is close in content to a merge prompt ("what happened, what was decided, what remains open"), without the first person or the automation. Lessons are an automated cousin of human-owned rules. Connectome enforces an as-of vantage by rule; cdocs gets both vantages from document type, though nothing enforces that a devlog stays as-of. Convergent practice. Both coordinate multiple agents through plain shared files, and neither uses a shared memory service.

Context · 24 systems

Where both sit in the memory landscape

Two axes from the landscape report's taxonomy separate these systems best: who writes the memory, and what it models about the agent. Agent harnesses are moving toward plain files as the durable store. Coding tools are also moving authorship back toward humans.

What the coding evidence says. Repo context files do not significantly raise success rates and cost about 20% more tokens (Gloaguen et al., including the CTXbench subset closest to cdocs). Summarized, correctly retrieved experience helps, while raw trajectories can hurt (SWE-ContextBench; Kim et al.). In DreamBench-SWE, no memory scores 11.7% and any memory scores 45–54%, but the benchmark does not rank memory architectures, and its non-inferable evidence favors a lossless archive as much as a curated corpus. Poisoned persistent memories reached up to 99.8% implant success. That risk applies to any memory agents read back, cdocs included. No study measures persistent identity's effect on task outcomes, in either direction. Several of these 2026 papers are single-author and were read at abstract level.

The identity question

Unmeasured, not refuted

"Identity" bundles several functions. Some already have a home outside identity. Two do not: calibrated judgment of a role over time (a reviewer never learns which of its findings were overturned) and self-knowledge ("I tend to over-claim tests pass"). Working-state continuity is covered partly, by handoffs, arc-state, and Pillar 3 specialists, but not across workstreams.

The case for a persistent self

  • Continuity of judgment. Every cdocs reviewer starts cold. The reviewer who caught this arc's pro-cdocs tilt carried nothing forward.
  • Re-onboarding. Current notes cut a follow-on session's re-reads from 8 files to 4, and peak context from ~334k to ~173k tokens. That result is evidence for memory in general, not identity. The identity-specific claim, that an agent's own memory carries tacit context a handoff omits, is untested.
  • Relationship. The corpus records who typed, not who caused. A self that remembers what this human pushed back on captures the steering the corpus drops.
  • Self-knowledge. A record like "my X claims were wrong N times" targets premature victory, a known coding failure.
  • Revealed demand. OpenClaw (~390k stars) ships an agent-editable SOUL.md. Letta, Honcho, Hermes, and Connectome make the self first-class.
  • Values and engineering overlap. "No words in models' mouths," fail-loud over-budget, credentials that stay out of context, and gating that defers instead of hiding are all good engineering too.

The case against

  • sharedFalse memories from unverified consolidation. In the "68 initiations" incident (Fig 09), a prompt-ordering bug compounded across merges. The mechanism is an unverified summarizer, not the first person. A cdocs handoff that says "tests pass" without evidence is the same failure.
  • identityAs-of is the wrong vantage for coding. "The bug turned out to be X" is the most valuable coding memory, and as-of minting forbids it.
  • identityRe-authoring other parties. Merges "re-claim others' lives" (observed 2026-07-27). The coding version is remembering a reviewer's finding as your own insight.
  • identityModel binding. This contradicts cdocs' model tiering. It is doctrine, not a hard constraint, but it is an operational liability.
  • identityinference Self-flattery. Nothing checks a mint against the record. The relationship vector (remembering what the human liked) is shared with any user memory.
  • sharedPoisoning and non-reproducibility. Up to 99.8% implant success in one study. Unseeded text in both systems. Git review lowers the exposure only as far as review actually happens.

Net. The case for identity rests on its functions, and some of its evidence supports memory in general. The case against splits in two. The shared risks (unverified consolidation, poisoning, non-reproducibility) argue for verifying all agent-written memory, cdocs' own included. The risks specific to identity are the as-of vantage, re-authoring others in a first-person merge, model binding, and possibly self-flattery. So the experiment should test the persistent self and its voice directly, and not only a stripped-down notes file.

Unresolved

Open questions

  • Does identity help coding at all? No study tests it. Option 4 is a small internal test, not an answer.
  • Who reviews consolidation and audits notes? Human review time is the scarce input for 1a and 4. Without it, the reviewed pattern turns back into the unreviewed one, and that applies to the existing corpus too.
  • What would calibration memory contain? "Findings later overturned" needs a ground-truth signal that reviews do not record today.
  • Transcript coverage and privacy. Transcripts are keyed by path and stay on one machine. For this repo they are split across at least five project directories: about 40 files against 87 devlogs. Committing them would be a larger decision.
  • Does Connectome's production behavior match its design? Which solver runs per resident is unverified. No published evaluation of recall accuracy or drift was found.
  • How should Connectome be judged on its own terms? Continuity, consistency, and self-model coherence need an evaluation axis that no source here supplies.
  • Where does an identity layer belong? Relationship and self-knowledge memory is naturally cross-repo. It may belong in the harness's user-level memory, not in cdocs.
