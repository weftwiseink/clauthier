Cdocs context roadmap

BLUF. Planning view first, evidence appendix last. Eight RFPs, four in motion right now: wip subagent labeling (a /cdocs:full-send is landing it as this loads), researching chat-record/devlog-management design and the haiku Bash-wrapper landscape (two sonnet /cdocs:reports in flight), and rfped graphify-scoped retrieval (an accepted proposal already exists; only devcontainer plumbing has landed).

Two levers were previously conflated and are now split: graphify cheapens each cold read (per-call scoping); a shared retrieval cache would stop the 97.4% cross-agent re-reads graphify never touches (no design exists for this yet — genuinely new territory, unresearched). Cap-and-reseed hard-depends on the chat-record/devlog substrate landing first. Prompt-cache-TTL tuning, upstream claude-usage bug filings, and a standalone measurement harness are out of scope for this roadmap (deprioritized / owned elsewhere — see appendix).

Scope caveat. Underlying numbers are one 7-day weftwise window (2026-09-12 to 09-20), dominated by loro-repo propose/implement loops (top 2 of ~40 sessions ≈ 75% of read intake). The role mix is workload-dependent; implementer dominance is a hypothesis about an implement-heavy week, not a certified structure — a re-measurement checkpoint sits at the end of Phase 2 and Phase 3. Read-volume token counts are approximations (chars ÷ 4).

5. Open questions and risks

  • Chat-record scope, still being researched. Per-subagent vs. overseer-only, and whether to wrap /compact or build a separate scratchpoint artifact, are exactly what the in-flight report is resolving — treat RFP-2's shape as provisional until it lands.
  • Graphify vs. shared cache are genuinely different problems. An earlier pass in this conversation conflated them; corrected here. Graphify scopes a single cold read; the shared cache would eliminate repeat cold reads across agents. Neither subsumes the other.
  • Graphify's MCP path is currently dead. The clauthier devcontainer's graphify CLI is confirmed live; its MCP server registration is shadowed by a host ~/.claude.json bind-mount collision. The fix lives in the lace repo, out of scope here; RFP-3 proceeds CLI-only per the existing proposal's own decision.
  • Sonnet overseer escalation reliability. Untested. The spike must measure when it consults the advisor and any routing/dispatch regression, not only cost.
  • Cap cutoff. 0.4–0.6M is a better starting guess than the source report's 0.2M, but still unmeasured until re-briefing is cheap (RFP-2 must land first).
  • Single-window bias. Implementer dominance may not hold in proposal- or debug-heavy weeks. Re-measure before over-tuning any cutoff or priority here.
  • Intentional Fable usage. 7.3% Fable-5.1 share is a maintainer decision (dense technical work); tiering work must not "correct" it toward the Opus floor.
  • Explicitly out of scope for this roadmap. Prompt-cache-TTL tuning across loop turns was considered and deprioritized ("not worth the squeeze"). Upstream claude-usage plugin bugs (agents.total_tokens 210×–1045× low; orphaned agent-ids) are that project's own workstream — our only obligation there is correct labeling (RFP-1). A standalone measurement-harness/dashboard RFP was dropped for the same reason.

D. Why re-reads happen

~4.7–5.0M whole-file Read tokens (~70% of whole-file-read volume) are re-reads. At true context granularity (one .jsonl = one window) the cause is structural.

E. Warm-implementer context (schematic)

A durable implementer re-bills its whole transcript as cache-read each turn. Measured: top implementer 924 turns, 18 rounds, per-round peak 155k → 966k, alone 11.3% of week cache-read; the 46 implementers are 54.8%; corr(rounds, carried context) = 0.89.

F. Architecture: which layer attacks which cost

Move long-lived context out of re-sent windows into durable documents plus cheap, scoped retrieval.
