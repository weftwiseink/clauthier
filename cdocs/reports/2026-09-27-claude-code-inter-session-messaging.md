# Native session-to-session messaging in Claude Code, and what it changes for the voice companion

> BLUF: Yes, Claude Code has a native, on-by-default (not labeled preview), subscription-compatible peer-messaging interface: **cross-session messaging** (`ListAgents`/`SendMessage`, `/list-agents`), documented at [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging). It works over local sockets on this machine and, when signed into claude.ai, over Anthropic servers to other machines and cloud sessions, no API key required. Its two sharp edges for the companion use case: **an idle session is woken and given the message as a fresh turn** (confirmed in docs, resolving the previous report's open question), and a session in `bypassPermissions` mode **holds inbound messages for the user's approval by default**, so a live `/oversee` running with `--dangerously-skip-permissions` will not silently accept spoken relays unless `crossSessionInbound` is set to `accept` for it (via `--settings` or user settings; a project-file `accept` does not apply) or the sender also runs in bypass mode. A second correction to the prior report: Anthropic's docs steer products built on the Agent SDK to Console API keys and forbid third-party developers from offering claude.ai login or routing requests through subscription credentials; the same legal page says this does not prevent an end user signing in to the unmodified Claude Code binary with their own subscription, and `claude -p` uses that login unless run with `--bare`. So an SDK-package-hosted overseer on a subscription is at best a policy gray area, while driving the unmodified `claude` CLI is not. Together this argues for cross-session messaging plus `notify_when_idle` as the companion's spine.

## Context / Background

[`2026-09-26-voice-companion-architecture.md`](2026-09-26-voice-companion-architecture.md) designed a talker/thinker split for a voice companion sitting beside an `/oversee` overseer session, and surveyed four ways to get the user's spoken answer back into a live overseer: Channels, Agent SDK `resume`, `claude -p --resume`, and MCP. The user asked whether Claude Code has a more native session-to-session interface, since the tools available to the very overseer session that requested this report (`ListAgents`, `SendMessage`, `FetchInboxMessage`, `ReadNotifications`, `RemoteTrigger`) already hint that it does, and specifically asked whether any of this works "with claude.ai subscriptions also," since the companion is meant to run alongside an interactive Claude Code session the user is paying for as a subscriber, not through a metered API key.

This report inventories every message-passing affordance in current Claude Code, answers the native-interface question directly, and re-maps the voice companion's read/write/notify needs onto the corrected landscape.

## Key Findings

- **Cross-session messaging is the native interface**, and it is not experimental: it ships on by default from Claude Code v2.1.224+ (native Windows v2.1.234+), with no flag to turn on. `ListAgents` discovers reachable sessions; `SendMessage` delivers text to one by name. [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging)
- **It works on a claude.ai subscription for every hop that matters here.** Same-machine delivery works on any provider, including plain OAuth login. Cross-machine and cloud delivery specifically **requires a claude.ai sign-in** as the session's active auth (Remote Control's requirement) and explicitly does **not** work with an API key or on Bedrock/Vertex/Foundry for that hop. This is the opposite polarity from the Agent SDK: cross-session messaging is subscription-native and gated *away* from API keys for the cross-machine case, while the SDK packages are steered toward API keys for products (see next finding).
- **The Agent SDK packages are steered to Console API keys; the unmodified CLI is not.** From the SDK's own docs: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead." [code.claude.com/docs/en/agent-sdk/overview](https://code.claude.com/docs/en/agent-sdk/overview). This is corroborated by a February 2026 policy clarification widely covered in the developer press (e.g. [The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/), [WinBuzzer](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/)); treat the secondary coverage as corroborating color, the doc line itself as the load-bearing claim. Scope matters: the [legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) aims the restriction at developers offering claude.ai login or routing requests "on behalf of their users", says it does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription", and notes Pro/Max limits "assume ordinary, individual usage of Claude Code and the Agent SDK". `claude -p` (documented as "the Agent SDK via the CLI") uses the subscription login unless started with `--bare`. Personal use of the Python/TypeScript SDK packages on one's own subscription is therefore ambiguous, not flatly barred; the safe reading is to build on the unmodified CLI.
- **A message wakes an idle receiver and starts a new turn.** Direct quote: "The receiving Claude reads the message between tool calls during an active turn, so a running tool is never interrupted. When the receiving session is idle, Claude Code starts a new turn with the message." This resolves the prior report's open question about whether the message plumbing can interrupt a genuinely idle overseer.
- **Permission-mode class gates inbound delivery by default.** When no explicit `crossSessionInbound` setting applies, Claude Code buckets sessions into "bypasses permission prompts" (`bypassPermissions`, and plan mode in an interactive terminal with bypass available) versus "prompts" (`auto`, `acceptEdits`, `dontAsk`, Manual). A bypass-mode receiver **holds** every inbound message for the user's approval unless the sender also identifies as bypass-mode. This means an `/oversee` run under `--dangerously-skip-permissions` (a real possibility for autonomous arcs) will not auto-accept the companion's relayed answers unless the overseer's own settings set `crossSessionInbound: "accept"`.
- **`notify_when_idle` is the built-in "needs you" push**, but it is deliberately narrow: main-conversation only (not subagents, not teammates), same-machine only, one-shot, 12-hour expiry, and it can be attached to a message or subscribed standalone with no tokens spent in the watched session.
- **Non-interactive (`claude -p`) sessions bind an inbox socket too**, unless started with `--bare`, so a long-running headless overseer can receive cross-session messages exactly like an interactive one. The receiving session's own class decides the default: a prompting `-p` session delivers by default (holding only messages from a bypass-mode sender), and a `bypassPermissions` `-p` session holds by default. A `-p` session can't show the approval dialog, so a default-held message is kept for `dialogExpiry` (five minutes) and then dropped; to accept unattended, start the worker with `crossSessionInbound: "accept"` in its `--settings`.
- **Messages are plain text only**, size-capped at roughly a million characters same-machine, with a 50-message accepted-but-unread queue and per-sender loop throttling. `@file`/`@resource` mentions are inert at the receiver: they arrive as literal text, not attachments.
- **Cross-machine and cloud messages route through Anthropic's servers**, not peer-to-peer; same-machine messages use a Unix domain socket (named pipe on Windows) and never leave the box. `isolatePeerMachines: true` forces a user-approval gate before anything leaves the machine, regardless of permission mode.
- **A one-way cross-machine message carries no reply address** if the sending session isn't itself connected to Remote Control at send time, matching the ground-truth note that cloud/Remote-Control targets "report nothing back" and "cannot message back yet" for cloud specifically. This report finds that framing is mostly right but the doc frames it as a reply-address property of the sender's own connection state, not a hard cloud-target limitation: a Remote-Control-connected sender *can* get replies routed back from a cloud session in principle, subject to the cloud session's own SendMessage support. Mark this nuance unverified since it wasn't directly tested.

## The native interface, in full

**What it is called.** "Cross-session messaging" in docs and CLI help; `/list-agents` (alias `/peers`) is the user-facing command; `ListAgents`/`SendMessage` are the tool names Claude itself calls. Addresses are bare session names; when several live sessions share a name, Claude adds a short identifier from its listing to disambiguate. As of Claude Code v2.1.232+, a user can also address a target directly in a prompt with `@name` autocomplete, which resolves the same way `SendMessage`'s `to` field does.

**Delivery semantics, precisely.**
- Mid-turn: delivered between tool calls, never interrupting a running tool.
- Idle: **starts a new turn**, spending the receiver's tokens like any prompt.
- Default holding: gated by the two-class permission-mode bucket described above; `crossSessionInbound` (`accept`/`hold`/`refuse`) overrides the default per-session, and only the user (not another session) can set it, so a companion cannot self-authorize its own inbound acceptance.
- Non-interactive `-p` sessions participate fully unless launched with `--bare`, which also strips OAuth/keychain reads and forces `ANTHROPIC_API_KEY`.
- No delivery receipt to the sender beyond "accepted or refused at send time"; a held message shows the receiving user a dialog, with a five-minute default expiry (`dialogExpiry`), extendable to `"never"`; in a background session with no terminal attached the dialog stays open past the deadline until someone attaches, and at most 100 held messages are kept.

**Trust model.** An incoming cross-session message is explicitly untrusted relative to the receiving user: it can't approve permission prompts, can't change `CLAUDE.md`/settings, and any embedded slash-command text is inert. This matches the "anti permission-laundering" rule already in the overseer's own `SendMessage` tool description, and is partly harness-enforced (a message can never answer a permission prompt, slash commands in it never execute, the receiver's permission prompts still fire) and partly instruction-level (Claude is instructed not to change settings or `CLAUDE.md` because another session asked).

**Maturity and auth.** On by default from v2.1.224, with no preview label on the docs page. Same-machine works on every provider (Anthropic API key, Bedrock, Vertex/Agent Platform, Foundry, and OAuth). Cross-machine and cloud both require a claude.ai sign-in via Remote Control and are unavailable on API-key-only or third-party-cloud auth. This is the one part of the whole inventory built specifically for subscription users reaching their own other subscription-backed sessions.

## Answering the user's question directly

**Yes**, there is a native session-to-session interface, and it predates and is broader than anything the prior report considered: **cross-session messaging** (`ListAgents`/`SendMessage`), with `notify_when_idle` as its companion primitive for "tell me when it's done." It is not "agent view" (that's the read-only `claude agents --json`/peek-reply surface) and not Channels (those are for non-Claude external sources). Docs: [cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging).

Its sharp edges, restated precisely from the docs rather than inferred:

1. **Idle wake is real and documented**, not just implied by the "queues and drains at next tool round" framing the overseer's own tool description gives. An idle receiver gets a fresh turn, at the receiver's token cost.
2. **Permission-mode approval holds are bidirectional-aware, not just "sender might be untrusted."** The receiving session's own class (bypass vs. prompting) decides the default, and it holds *more* aggressively when the receiver itself bypasses prompts, precisely because a bypass-mode session has no human in the loop to catch a bad inbound message otherwise. For `/oversee` run with `--dangerously-skip-permissions`, this means the companion's replies will queue for the user's own approval by default unless the overseer's launch settings set `crossSessionInbound: "accept"` explicitly, which is worth deciding deliberately, not by accident.
3. **No receipts to Remote Control/cloud targets**, confirmed: `SendMessage` to those targets reports "delivered" (or not) at send time only, no read receipt, matching the ground truth.
4. **Cloud targets may not reply**: the overseer's own tool description says cloud sessions "cannot message back yet"; the docs themselves only say a send from a session not connected to Remote Control carries no reply address. Treat as unverified.

## Mapping onto the voice companion's three jobs

**(i) A read feed of overseer state and pending questions.** Unchanged from the prior report: `claude agents --json` plus `claude logs` remains the thin, stable, local, auth-agnostic feed. Cross-session messaging doesn't replace this; it's a push channel for *events*, not a queryable state snapshot. Use both: `agents --json` for "what's the current state," cross-session messaging (or `notify_when_idle`) for "tell me the moment something changes."

**(ii) Injecting the user's condensed answer into a live overseer, without the unsafe concurrent-resume problem.** This is where cross-session messaging is a strict upgrade over everything the prior report proposed:
- It is documented as safe against exactly the hazard the prior report worried about (`resume` interleaving into one transcript): a cross-session message is explicitly designed to arrive as a *new turn or between tool calls*, never as a concurrent write into the same transcript stream.
- It requires no special launch-time flag on a prompting-mode overseer (unlike Channels' `--channels`), and no architecture change (unlike hosting the overseer, which on a subscription should use the unmodified CLI rather than the SDK packages). A bypass-mode overseer needs `crossSessionInbound: "accept"` via `--settings` at launch or in user settings, or a bypass-mode sender.
- Its cost is the permission-mode hold behavior above, which needs a deliberate `crossSessionInbound` decision for a bypass-mode overseer, and its plain-text-only nature, which is fine for a condensed spoken answer.

**(iii) The overseer pushing a "needs you" event to the companion.** Two options, not mutually exclusive:
- `notify_when_idle`, if the companion is itself a Claude Code session on the same machine: one-shot, cheap, no polling.
- Cross-session `SendMessage` from the overseer itself, which it can already do unprompted "when it sees the need," per docs, e.g. after hitting an escalation. This is a better fit than the prior report's reliance on `Notification` hooks alone, since the overseer's own Claude-driven judgment decides *when* to escalate to the companion, not just "a permission prompt fired."

### Candidate companion designs, ranked

1. **Companion is itself a Claude Code session (interactive or `claude -p` with a bound inbox socket), using `SendMessage` both ways plus `notify_when_idle`.** Works today, subscription-native, no flags, no ToS risk. The companion's "brain" can still be a small model via `--model` or `CLAUDE_CODE_SUBAGENT_MODEL`-style overrides, but note: a `claude -p` process is still a full Claude Code session, heavier than a bare Pipecat pipeline calling a small model directly. This is the top recommendation for the write-back leg specifically; it can coexist with a separate Pipecat/audio front that treats this session as its "overseer proxy," per (2) below.
2. **Companion is a non-Claude process (Pipecat app) that drives a small dedicated Claude Code session as its proxy into cross-session messaging**, rather than talking to the overseer directly. The Pipecat app owns audio; the proxy session owns `SendMessage`/`ListAgents`/`notify_when_idle` and exposes them to Pipecat over a local IPC of the builder's choosing (a Unix socket, a tiny MCP server the Pipecat app hosts, or literally shelling out to `claude -p` per message). This avoids needing the audio process to reimplement Claude Code's own auth and socket protocol, and keeps the companion subscription-authenticated because the proxy session is an ordinary Claude Code session.
3. **Companion drives a named session over Remote Control** rather than a local proxy: viable if the companion truly needs to run off-machine, but adds the Anthropic-server hop and its associated latency for every message, worse than (1)/(2) for a local desktop companion.
4. **A Channel MCP server as the product surface** remains attractive specifically for permission-relay (letting the companion approve/deny tool use, not just answer questions), but stays gated by research-preview status and, for Team/Enterprise accounts, an admin flag. For a personal subscription with no org, it needs only `--channels` at overseer launch, no admin step, which is friendlier to the "just works on a subscription" requirement than the prior report's framing suggested, though it still needs the overseer relaunched with the flag, which cross-session messaging does not.

**Recommended combination:** cross-session messaging (design 1 or 2) as the default spine for both read-push (`notify_when_idle`) and write-back (`SendMessage`), with `claude agents --json` as the pull-based state feed underneath it, per the prior report's option (a). Reserve Channels' permission relay for a later phase specifically when "approve/deny tool use from voice" becomes a real requirement, since that is the one thing cross-session messaging structurally cannot do: an inbound message can never itself approve a pending permission prompt.

## Unverified claims

- Whether a cloud session that a Remote-Control-connected local session messaged can, in some cases, actually reply back (the docs' "except in the one-way cross-machine case" carve-out is ambiguous about whether it covers cloud targets too, versus only other-machine Remote Control targets); the docs elsewhere state flatly that cloud sessions "cannot message back yet" per this report's own ground truth, so this is likely resolved in favor of "no," but the exact wording wasn't pinned to a single unambiguous sentence in the fetched page.
- `RemoteTrigger`/routines' ability to post into an *existing* named session, as opposed to only spawning a fresh cloud session, was corroborated only via search-result summaries of [code.claude.com/docs/en/routines](https://code.claude.com/docs/en/routines), not a direct fetch of that page's full text in this pass.
- Whether `claude --bg` (background local session) can be launched with `--channels` simultaneously remains open from the prior report; cross-session messaging sidesteps this specific question since it needs no launch-time flag, but the combination wasn't independently retested here.
- The precise interaction between agent-team teammate messaging and cross-session messaging when a teammate is also a valid `SendMessage` target outside its team (the docs say "denying `SendMessage` also removes messaging to subagents and agent-team teammates, since the same tool serves both," implying one unified tool, but this report did not test whether a non-team session can message a teammate directly by name).
