# Native session-to-session messaging in Claude Code, and what it changes for the voice companion

> BLUF: Yes. Claude Code has a native, on-by-default, subscription-compatible peer-messaging interface: **cross-session messaging** (`ListAgents`/`SendMessage`, `/list-agents`), documented at [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging). It works over local sockets on this machine and, when signed into claude.ai, over Anthropic servers to other machines and cloud sessions, no API key required. Its two sharp edges (detailed once, in Key Findings): an idle receiver is woken and given the message as a fresh turn, and a `bypassPermissions`-mode receiver holds inbound messages for the user's approval by default. A second correction to the prior report: Anthropic restricts *third-party products* from offering claude.ai login or routing requests through subscription credentials on their users' behalf; it explicitly does not restrict an end user signing the unmodified `claude` binary into their own subscription, including `claude -p`. So hosting `/oversee` from the companion via the unmodified CLI, not the SDK packages, is back on the table and is in fact the only design that gets native, in-band visibility into every permission prompt, at the cost of the companion becoming the launcher instead of the user's terminal.

## Context / Background

[`2026-09-26-voice-companion-architecture.md`](2026-09-26-voice-companion-architecture.md) designed a talker/thinker split for a voice companion sitting beside an `/oversee` overseer session, and surveyed four ways to get the user's spoken answer back into a live overseer: Channels, Agent SDK `resume`, `claude -p --resume`, and MCP. The user asked whether Claude Code has a more native session-to-session interface, and specifically whether it works "with claude.ai subscriptions also," since the companion is meant to run alongside an interactive session the user is paying for as a subscriber.

The overseer session that requested this report is itself primary evidence: as a subscription-authenticated Claude Code CLI session, its own `ListAgents` tool reaches 8 local tmux-hosted sessions and 5 Remote Control sessions today (per that tool's own description, not the docs page), confirming cross-session messaging's subscription reach empirically, not just on paper.

This report inventories every message-passing affordance in current Claude Code, answers the native-interface question, and re-maps the voice companion's read/write/notify needs onto the corrected landscape.

## Key Findings

- **Cross-session messaging is the native interface**, on by default from Claude Code v2.1.224+ (native Windows v2.1.234+), no preview label, nothing to enable. `ListAgents` discovers reachable sessions; `SendMessage` delivers text to one by name. [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging)
- **Subscription reach.** Same-machine delivery works on any provider, including plain OAuth login. Cross-machine and cloud delivery requires a claude.ai sign-in as the session's active auth (Remote Control's requirement) and does not work with an API key or on Bedrock/Vertex/Foundry for that hop.
- **The Agent SDK packages are steered to Console API keys; the unmodified CLI is not.** From the SDK docs: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods described in the Quickstart instead." [code.claude.com/docs/en/agent-sdk/overview](https://code.claude.com/docs/en/agent-sdk/overview). Scope matters: the [legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) aims the restriction at developers offering claude.ai login or routing requests "on behalf of their users," states it does not "prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription," and notes Pro/Max limits "assume ordinary, individual usage of Claude Code and the Agent SDK." `claude -p` (documented as "the Agent SDK via the CLI") uses the subscription login unless started with `--bare`. Personal use of the Python/TypeScript SDK *packages* on one's own subscription is therefore a policy gray area, not flatly barred; driving the unmodified CLI is the safe reading and is corroborated by press coverage of a February 2026 policy clarification ([The Register](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/), [WinBuzzer](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/)).
- **Idle wake.** Verbatim from the docs: "The receiving Claude reads the message between tool calls during an active turn, so a running tool is never interrupted. When the receiving session is idle, Claude Code starts a new turn with the message." This resolves the prior report's open question about interrupting a genuinely idle overseer, and it is the only place this report states the idle-wake behavior.
- **Bypass-mode hold.** When no explicit `crossSessionInbound` setting applies, a receiver is bucketed as "bypasses permission prompts" (`bypassPermissions`, and plan mode with bypass available) or "prompts" (`auto`, `acceptEdits`, `dontAsk`, Manual). A bypass-mode receiver holds every inbound message for the user's approval unless the sender also identifies as bypass-mode. `crossSessionInbound: "accept"` overrides this, but only from `--settings`, user settings, or managed settings: a *project or local* `accept` is ignored, since precedence rules apply project/local values only when they are stricter than the default. This is the only place this report states the bypass-hold rule; every other mention below points back here.
- **`notify_when_idle`** is the built-in "needs you" push: main-conversation only, same-machine only, one-shot, 12-hour expiry, no tokens spent in the watched session. Because it is one-shot, a companion that wants ongoing idle notices must re-subscribe after each one fires; `/oversee` idles at the end of nearly every turn, so this is a re-subscribe-per-turn pattern, not a standing subscription.
- **Non-interactive (`claude -p`) sessions bind an inbox socket too**, unless started with `--bare`, so a headless overseer receives cross-session messages like an interactive one, gated by the same bypass-hold rule above. A `-p` session can't show an approval dialog, so a default-held message is kept for `dialogExpiry` (five minutes) and dropped; to accept unattended, start the worker with `crossSessionInbound: "accept"` in its own `--settings`.
- **Messages are plain text only**, capped at roughly a million characters same-machine, a 50-message accepted-but-unread queue, and per-sender loop throttling. `@file`/`@resource` mentions are inert at the receiver: literal text, not attachments.
- **Routing.** Cross-machine and cloud messages route through Anthropic's servers; same-machine messages use a Unix domain socket (named pipe on Windows) and never leave the box. `isolatePeerMachines: true` forces a user-approval gate before anything leaves the machine, regardless of permission mode. No delivery receipt reaches the sender beyond "accepted or refused at send time," so Remote Control and cloud targets report nothing back once a message is in flight.
- **Cloud targets may not be able to reply.** The overseer's own tool description states cloud sessions "cannot message back yet"; the docs themselves say only that a one-way send from a sender not connected to Remote Control carries no reply address. Treated as unverified below, since the two statements aren't the same claim.

## The native interface, in full

**What it is called.** "Cross-session messaging" in docs and CLI help; `/list-agents` (alias `/peers`) is the user-facing command; `ListAgents`/`SendMessage` are the tool names. Addresses are bare session names; when several live sessions share a name, Claude adds a short identifier to disambiguate. As of v2.1.232+, a user can also address a target in a prompt with `@name` autocomplete, resolved the same way `SendMessage`'s `to` field is.

**Trust model.** An incoming message is explicitly untrusted relative to the receiving user: it can't approve permission prompts, can't change `CLAUDE.md`/settings, and any embedded slash-command text is inert. This is partly harness-enforced (a message can never answer a permission prompt, slash commands never execute, the receiver's own permission prompts still fire) and partly instruction-level (Claude is told not to change settings because another session asked).

**Maturity and auth.** On by default from v2.1.224, no preview label. Same-machine works on every provider. Cross-machine and cloud both require a claude.ai sign-in via Remote Control and are unavailable on API-key-only or third-party-cloud auth: the one part of this inventory built specifically for subscription users reaching their own other subscription-backed sessions.

## Mapping onto the voice companion's three jobs

**(i) A read feed of overseer state and pending questions.** `claude agents --json` plus `claude logs` remains the thin, stable, local, auth-agnostic feed; a plain non-Claude process can shell out to it directly, no Claude-session peer required. Cross-session messaging is a push channel for *events*, not a state snapshot: use both.

**(ii) Injecting the user's condensed answer, without the unsafe concurrent-resume problem.** Cross-session messaging is designed for exactly this hazard: a message arrives as a new turn or between tool calls, never as a concurrent write into the live transcript. It needs no launch-time flag on a prompting-mode overseer, and a bypass-mode overseer just needs `crossSessionInbound: "accept"` at launch (or a bypass-mode sender, which then also acts without prompts itself, a trade-off worth naming). Direct inbox-socket posting is a lighter-weight variant for a non-Claude writer specifically (below).

**(iii) The overseer pushing a "needs you" event to the companion.** `notify_when_idle` if the companion is itself a Claude Code session (re-subscribed after every notice), or unprompted `SendMessage` from the overseer when its own judgment decides an escalation matters, a better fit than relying on `Notification` hooks alone.

### Candidate companion designs, ranked

**0. Companion hosts the overseer**, launching `/oversee` itself via `claude -p --input-format stream-json --output-format stream-json --permission-prompt-tool <mcp-tool-or-stdio>`, on the unmodified CLI with the user's own subscription login. This is the only design that sees every permission request and every `AskUserQuestion` natively and in-band: the harness routes each one straight to the tool the companion registers, with no hold, poll, or relay step. The cost is real: `/oversee` is no longer launched from the user's own terminal, the companion becomes its sole launcher and owner of its stdin, and the user trades "just type `claude` in my terminal" for a companion-managed session lifecycle (attach, detach, view logs). Rank this first *if* that trade is acceptable; it is strictly more capable on permission visibility than every design below, none of which can relay a permission approval at all.

**1. Companion is itself a Claude Code session (interactive or `claude -p` with a bound inbox socket)**, on the side, using `SendMessage`/`ListAgents` both ways plus `notify_when_idle`, against an overseer the user still launches themselves. Zero-friction retrofit onto an existing workflow, subscription-native, no flags. Its structural gap versus design 0: it cannot relay a permission prompt, only ordinary conversational turns, so a bypass-mode overseer is the only way to avoid the approval-hold dance, and a companion also running bypass-mode inherits that trade-off (delivered without a settings change, but acting without prompts itself).

**2. Companion is a non-Claude process (Pipecat) polling and posting directly, no proxy Claude session at all.** Given (i) `claude agents --json` is a plain CLI command any process can shell out to, and (ii) direct inbox-socket posting lets a non-Claude writer post write-back straight into the overseer's socket (path published via a `SessionStart` hook), the "small dedicated proxy session" from the prior draft of this report is no longer necessary for either the read leg or the write leg. What a non-Claude process still cannot do on its own is *receive* an overseer-initiated push (`SendMessage`/`notify_when_idle` targets must be Claude sessions), so a hybrid is likely: direct socket write-back, direct `agents --json` polling for read, and either a thin proxy Claude session kept alive purely to receive pushes, or tighter polling of `waitingFor` as a substitute for push. The socket's message-line wire format after the optional auth line is not spelled out in the docs; verify empirically (for example with `socat` against a scratch session) before building on it.

**3. Companion drives a named session over Remote Control.** Viable only if the companion must run off-machine; adds the Anthropic-server hop and its latency to every message, worse than (1)/(2) for a local desktop companion.

**4. A Channel MCP server as the product surface.** The only design besides (0) with a documented permission-relay path, but gated by research-preview status; for a personal subscription with no org it needs only `--channels` at overseer launch, no admin step, but still requires relaunching the overseer with that flag, which (1)/(2) do not.

**Recommended combination:** if the companion launching `/oversee` is acceptable, design 0 is the strongest single answer, since it is the only one with native permission-prompt visibility and needs no separate write-back mechanism at all. If the user wants to keep launching `/oversee` themselves, combine (1) or (2) for read/write/notify, with (4)'s permission relay as the later addition once "approve/deny tool use from voice" becomes a real requirement, since cross-session messaging and direct socket posting can never approve a permission prompt.

1. **The "How answers get back in" table's "Agent SDK hosting the overseer" row is now "CLI-hosting the overseer."** Drive the unmodified `claude` CLI in stream-json mode with `--permission-prompt-tool`, not the SDK packages, which are steered to Console API keys and are a policy gray area for personal subscription use. Materially lower friction than every other option except peek-reply, since it needs no launch-time flag.
3. **Option (a) "Thin translation sidecar"'s write path** should add both cross-session messaging and direct inbox-socket posting as options that beat "human answers in the agent-view peek panel," since both work unattended and neither needs Channels' research-preview status.

5. **The architecture diagram's bridge node** should read: cross-session messaging (write) / direct socket posting (write, non-Claude) / CLI-hosted overseer via stream-json (read+write, native permission relay) / forked resume (read-only).
6. **`notify_when_idle` was not mentioned at all** in the prior report and answers part of the "triage policy" open question, with the caveat that it is one-shot and needs re-subscription after every notice, which `/oversee`'s near-every-turn idling makes frequent.

## Unverified claims

- Whether a cloud session can reply to a Remote-Control-connected sender: the overseer's own tool description says "cannot message back yet," the docs only describe a reply-address rule for one-way cross-machine sends; the two aren't the same claim.
- Whether a routine (`RemoteTrigger`) can post into an *existing* named session rather than only spawning a fresh cloud session: no support found in the routines docs; dropped from the design recommendations accordingly.
- The exact message-line wire format for direct inbox-socket posting after the optional `{"type":"auth",...}` line: the docs describe the socket, the auth line, and the delivery/hold rules, but not the payload schema itself. Needs empirical verification before relying on it for the Pipecat write-back path.
- Whether `claude --bg` can be launched with `--channels` simultaneously: open from the prior report; cross-session messaging and direct socket posting both sidestep the question by needing no launch-time flag, so it matters only for design 4.
