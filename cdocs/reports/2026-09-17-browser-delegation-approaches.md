# Delegating browser work off the lead model: architectures and streamlined tooling for a clauthier browser-delegation plugin

> BLUF: Architectures are compositional, not exclusive — the real axis is "who holds the tool-call loop," and MCP servers do not by themselves move the loop off the lead unless a cheaper subagent is the one calling them. The recommended default (reference, not decision) is an in-harness sonnet-tier subagent that holds the loop and drives a browser toolset, opus/fable never touches the browser directly, and the existing cdocs visual-review discipline (VLM-looker, `review_proof`, R1-R6) already defines the verdict layer this plugin should reuse rather than reinvent. A2A is real infrastructure for cross-harness/cross-org delegation but is over-scoped for same-org session reuse, which clauthier's own durable-specialist pattern (`orchestration-discipline.md` Pillar 3) already covers. On tooling, weftwise's raw, version-pinned Playwright MCP has recurred as a regression three times in 2026 (2026-01-18, 2026-05-18/24, 2026-07-25) and is already three patch releases stale against upstream at write time; Anthropic's own first-party browser-use toolset sidesteps that whole failure class and is the strongest exploratory candidate for the plugin's default capture leg.

## Context / Background

This report is the first of two Sonnet reports scoped by `cdocs/devlogs/2026-09-17-browser-delegation-plugin.md` ahead of a `/propose-revise` for a new clauthier plugin: letting high-judgment models (opus, fable) delegate browser work, UI verification, and minor UI tweaking to a cheaper/specialized delegate agent, harness, or process, potentially over MCP or A2A. A companion Report B (isolation and parallelization: multiple concurrent browser instances/contexts, `.lace/` port/mount assignment machinery) covers session concurrency and is out of scope here except where it bears on architecture choice.

Two 2026-08 reports already did the visual-verification-specific groundwork and this report builds on them without re-deriving:

- [Visual-review gaps and pixel-grounding handoff](2026-08-04-visual-review-gaps-and-pixel-grounding-handoff.md) established the R1-R6 discipline (DOM/widget-tree-blind lookers, measurement-proves-presence-never-absence, a tightened `review_proof` contract, a judge that may look on visual loops, ensemble lookers, ImageMagick `compare -metric AE` as the objective gate).
- [Visual frontend verification skills and tools: a web survey for cdocs](2026-08-05-visual-verification-skills-web-survey.md) already surveyed the visual-regression/VLM-judge market and concluded cdocs should adopt commodity capture and pixel-diff plumbing (webapp-testing, Chrome DevTools MCP, ImageMagick) but must own the VLM-looker judgment itself, because no vendor sells "does this render match this mock" as a first-render correctness judge.

This report asks a different, broader question those two do not: not "how do we verify a render is correct" but "who should be driving the browser at all, and through what channel, so the lead model's expensive context is not tied up doing it." It treats the R1-R6 verdict discipline as settled and asks how a *delegation* layer feeds it.

Grounding read: weftwise's current browser stack (`../../weftwise/main/scripts/playwright-mcp-launch.sh`, `../../weftwise/main/.mcp.json`) runs a single version-pinned `@playwright/mcp@0.0.78` server, executable-path-pinned to a specific `chromium_headless_shell` revision in lockstep with the devcontainer Dockerfile, with artifacts landing in `.playwright-mcp/`. weftwise's `CLAUDE.md` sets an Opus-4.8 floor for all dispatched work with an explicit named carve-out: "Always use Sonnet for search, explore, bash/git tedium, and straightforward research aggregation" — the model-tiering precedent this plugin should follow, per `plugins/cdocs/rules/model-tiering.md`.

## Key Findings

- **The pinned-Playwright-MCP setup is not hypothetically fragile; it has regressed three times in 2026.** weftwise's `cdocs/reports/2026-07-25-dev-environment-and-test-debt.md` documents a version bump from `0.0.75` to `0.0.78` silently changing `playwright-core`'s default browser-channel resolution, breaking the same devcontainer launch path for the third time (prior incidents: 2026-01-18, 2026-05-18/2026-05-24), each fix correct only for the upstream version current at the time. Verified directly against the live npm registry during this research: `@playwright/mcp`'s current published version is `0.0.81` (2026-09-14), three patch releases past weftwise's pinned `0.0.78` — the staleness clock the prior report warned about is already running.
- **An MCP server does not, by itself, move the tool-call loop off the lead model.** MCP is a client-calls-server protocol; unless the server uses the `sampling` primitive to drive its own sub-loop (rare, and design-intended for the opposite direction — server asks the client's model to complete something, with a human approval gate on both ends per the spec), every intermediate browser action (navigate, click, read a11y tree, screenshot) is a tool call the *calling* model pays context and turns for. If the lead calls a browser MCP server directly, the lead is still the one driving the browser step by step; the delegation only happens when a cheaper agent is the MCP client instead of the lead.
- **Playwright MCP returns the accessibility tree, not pixels, by design** (already flagged in the 2026-08-05 survey) — this keeps token cost low for functional automation but is exactly the "it's in the tree" measurement layer R2 forbids as proof-of-absence for a visual floor. It is a fit for the delegate's *driving* (navigate, fill forms, click) and a poor fit for the delegate's *verdict*.
- **Anthropic's own browser-use tool is a first-party alternative that sidesteps the whole version-pinning failure class.** Per Anthropic's platform docs (`platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool`, fetched and verified directly), the current production computer-use toolset is `computer_toolset_20260801`, and the same page explicitly contrasts it with a separate **browser use tool**: "For tasks that stay inside webpages, the browser use tool is the closer fit: its member tools read and act on the page itself, and it doesn't need a full desktop environment." Browser use reads the accessibility tree directly (not screenshots) and is a first-party client toolset — no npm package, no Chromium revision to pin, no devcontainer binary path to keep in lockstep with a launcher script. Secondary sources (not independently primary-verified against a dated Anthropic post: `enterprisedna.co`, `channelinsider.com`, `thenewstack.io`, `digitalapplied.com`) report an August 19, 2026 GA alongside computer use, Skills API, and Files API; the `20260801` toolset-name convention is corroborating but not itself a dated announcement. Treat the exact GA date as secondary-sourced; the tool's existence and behavior are primary-verified.
- **Anthropic's consumer "Dispatch" computer-use feature is a distinct thing from the API-level toolset, and the two are easy to conflate.** `claude.com/blog/dispatch-and-computer-use` (fetched, dated 2026-03-23) describes a macOS/Windows desktop app in "research preview" for Pro/Max subscribers pairing with a mobile app — this is a consumer product surface, not the `computer_toolset_20260801` / browser-use-tool API surface used in an agent harness. A proposal building this plugin should cite the API-level toolset, not the Dispatch app.
- **chrome-devtools-mcp is an official Google/Chrome-team MCP** (verified via `github.com/ChromeDevTools/chrome-devtools-mcp/`), adding screenshot capture, network-request analysis, performance tracing with actionable insights, and console monitoring on top of what Playwright MCP's accessibility-tree-only output provides. This is squarely the "capture leg" role the 2026-08-05 survey already recommended wrapping rather than building; it complements, not replaces, a selector-driving tool.
- **Playwright itself now ships an agent layer (Planner, Generator, Healer) built into Playwright core as of v1.56**, not a separate package (search-verified across multiple 2026 practitioner writeups — testdino.com, shiplight.ai, qaskills.sh, testmuai.com, firm86.com — but not independently primary-fetched against Playwright's own docs; treat as needing a primary-source confirmation pass before a proposal relies on exact CLI/config shape). The **Healer** agent specifically targets the "minor UI tweaking" seam this plugin cares about: given a failing test, it replays steps, inspects the current UI for an equivalent element, proposes a locator/wait patch, and re-runs until green. Documented integration targets reportedly include `vscode`, `claude`, `codex`, and `opencode` — if accurate, this is a directly clauthier-relevant affordance for the narrow case of "the UI changed slightly and a selector broke," distinct from a genuine visual/design fix.
- **browser-use (the open-source project) and Stagehand (Browserbase) both trade determinism for natural-language driving.** browser-use ships both a local stdio MCP server (bring-your-own LLM key) and a hosted Cloud MCP server (no setup, API key only) per its own docs (`docs.browser-use.com`, search-verified). Stagehand v3 (Feb 2026, per Browserbase's own blog and docs, search-verified) rewrote around four primitives (`act`, `extract`, `observe`, `agent`), talks to the browser directly via CDP for lower latency, added parallel multi-browser sessions, and progressively converts AI-identified actions into deterministic replay scripts to cut cost over time. Both introduce a second LLM-in-the-loop cost center and a vendor/runtime dependency; neither is a drop-in Playwright-MCP replacement, and neither judges correctness against a design reference — they are driving tools, not verifiers, same posture the 2026-08-05 survey found across the whole regression-tooling market.
- **A2A (Agent2Agent) is a real, governed standard, not vaporware, but solves a different problem than same-org session reuse.** Verified against `a2a-protocol.org`: Google donated A2A to the Linux Foundation, a v1.0 stable release exists, and the protocol defines Agent Cards (capability discovery) and a stateful task lifecycle (create/observe/complete) for agents that are independent systems across ownership/trust boundaries. That boundary-crossing is the point of A2A; a clauthier plugin operating entirely inside one Claude Code (or OpenCode) session/org does not have that boundary to cross, and already has a same-process answer: `orchestration-discipline.md`'s Pillar 3 durable-specialist pattern (resume-by-name via `SendMessage`, one specialist per active workstream) gives "a long-lived agent the lead converses with across many turns, holding its own session state" without standing up a second protocol or process.
- **The cdocs reviewer agent is already structurally forbidden from editing source** (`plugins/cdocs/agents/reviewer.md`: "Only `Edit` the target document's `last_reviewed` frontmatter: do not modify any other field, the body content, or any source file"). A browser delegate that both verifies AND patches minor CSS/UI issues would either need to be a distinct persona from that reviewer discipline or would erode the single-writer/reviewer-never-edits separation the rest of cdocs relies on for trustworthy verdicts.

## Delegation Architectures

The framing that resolves most of the apparent choice here: **architecture is a product of two independent axes**, not a single menu of mutually exclusive options.

1. **Who holds the tool-call loop** (the lead itself, an in-harness subagent, or a separate long-lived process/harness).
2. **What the loop-holder calls** (a browser MCP server, a first-party browser/computer-use toolset, or raw vision/computer control).

| Architecture | Who holds the loop | Session/state persistence | Token cost to the lead | Isolation | Where it fits |
|---|---|---|---|---|---|
| **In-harness subagent delegation** (Task/Agent tool, sonnet-tier delegate) | The dispatched subagent, for the duration of its turn | None across dispatches by default; a *durable specialist* (Pillar 3, resume-by-name) persists a browser session across many lead turns without a new protocol | Low — lead sees only the returned summary/verdict, not every click | Container/worktree isolation is a property of the dispatched agent (`orchestration-discipline.md`) | Default for "drive the browser, capture, report" drudgery; matches the model-tiering search/explore tier |
| **MCP-based delegation** (lead calls the MCP server directly) | The **caller**, i.e. still the lead unless a cheaper agent is the caller | State lives in the MCP server's browser-context process; the *decision* loop is the caller's, not the server's | High if the lead is the caller — every intermediate step burns lead context; low if a subagent is the caller instead | None inherent; e.g. Playwright MCP's single global context and `.playwright-mcp/` artifact dir | Correctly scoped as the *tool* a delegate calls, not as delegation on its own |
| **A2A / separate long-lived harness** | The remote agent, conversed with at task-boundary granularity (Agent Cards, stateful task lifecycle) | First-class and cross-process by design — this is A2A's actual selling point | Lowest per-step lead cost (the lead never sees intermediate tool calls at all, only task create/observe/complete) | Cross-process/cross-org isolation is the point | Cross-harness or cross-org delegation (e.g., handing browser work to a non-Claude-Code agent or vendor service); over-scoped for same-org session reuse, where the durable-specialist pattern is cheaper |
| **Computer-use / vision-driven control** (`computer_toolset_20260801`) | Whichever agent invokes it holds the screenshot-click-screenshot loop | Session = the desktop; no structured page state | Highest per action (vision round-trips) | None | Escape hatch: canvas apps, no accessibility tree, or when browser-use/Playwright's structured access is insufficient |
| **Browser-use tool** (first-party, `platform.claude.com` toolset sibling to computer use) | Whichever agent invokes it | Reads the live page's accessibility tree per call; no separate browser-process pinning concern | Lower than vision-driven; comparable to Playwright MCP's a11y-tree posture | None inherent, but no version/binary-pinning surface at all | Candidate default for the delegate's driving leg, specifically because it removes weftwise's recurring pin-and-regress failure class |

**Where "minor UI tweaking" should live.** The cdocs visual-review discipline already answers most of this by extension: R1-R6 keep the *verdict* (does this render match the mock) as a fresh, opus-class judgment the market does not sell, fed by a screenshot the delegate captures. The open question this plugin adds is what happens when the verdict is "wrong, and the fix is trivial" (a hex value, a padding number, a broken locator):

- **Locator/selector breakage** (the UI structure shifted slightly, no visual/design judgment required): Playwright's Healer agent (if the integration claim above holds up under primary verification) is a purpose-built, narrow-scope fit — it repairs the test, not the app, and needs no code-editing authority over the actual UI source.
- **A genuine visual/design fix** (wrong color, wrong spacing, wrong DOM structure): should stay with the existing implementer role in cdocs' implement/review loop, not the browser delegate, to preserve the reviewer-never-edits-source separation `reviewer.md` already encodes. The delegate's job stops at producing the `review_proof` artifact (screenshot plus region-by-region divergence per R1, or a bounded `compare -metric AE` result per R6); the fix is a normal implementer turn informed by that artifact.
- **A genuinely trivial fast-path** (delegate proposes a one-line patch, lead reviews and applies it) is plausible but is scope creep against the existing reviewer/implementer separation and is flagged below as an open question rather than a recommendation — it blurs a boundary the rest of cdocs deliberately keeps sharp.

|---|---|---|---|---|---|---|

| **cdocs visual-review discipline (VLM-looker, ImageMagick `compare -metric AE`)** | N/A — a prompt-plus-fresh-subagent pattern, not a dependency | N/A | Consumes screenshots from any of the above | Model tokens only (a subagent turn) | As fast as spawning a fresh subagent | This IS the verdict layer; nothing above substitutes for it (2026-08-05 survey's core conclusion) |

The throughline matches the 2026-08-05 survey's verdict, extended one layer down: cdocs should keep adopting commodity *capture and driving* plumbing (now including the first-party browser-use tool as the strongest capture-leg candidate) and keep owning the *judgment* — both the R1-R6 visual verdict and the new decision this report adds, which is *who is cheap enough to hold the loop while capturing it*.

## Fit into cdocs/clauthier

- **Model tiering.** The delegate's *driving* work (navigate, click, screenshot, capture) is squarely the Search/Explore tier (`plugins/cdocs/rules/model-tiering.md`): sonnet by default, matching weftwise's own named carve-out ("Always use Sonnet for search, explore, bash/git tedium, and straightforward research aggregation" above its Opus-4.8 floor). The delegate's *verdict* — a fresh looker judging a render against a mock — stays opus-class, per the existing `reviewer`/`judge` agents (`model: opus`) and the model-tiering rule's explicit instruction not to downgrade judgment work. A browser-delegation plugin should carry this split as a first-class default, not leave it to be rediscovered per-consumer.
- **Relation to `/cdocs:iterate` and `/cdocs:review`.** The delegate's captured screenshot (or `compare -metric AE` result) is exactly the artifact the tightened `review_proof` contract (R3 of the pixel-grounding handoff) already requires for a visual floor's `confirmed` row. The plugin's value-add is upstream of that contract: it gets the pixel into the reviewer's hands without the reviewer (or the lead) having to drive the browser itself. This is additive to, not a replacement for, the R1 DOM/widget-tree-blind looker pass — the looker still needs to be fresh and unconditioned; it just receives its screenshot from a delegate instead of capturing it inline.
- **Durable specialists over A2A for session reuse.** `orchestration-discipline.md` Pillar 3 (resume-by-name via `SendMessage`, one specialist per active workstream) already gives the plugin "a browser agent the lead can converse with across many turns, holding a logged-in session or multi-step flow" without introducing a second protocol. A2A's marginal value is specifically cross-harness/cross-org delegation (e.g., delegating to a non-Claude-Code agent, or a vendor's hosted browser-agent service) — worth naming as a documented future escalation path in the plugin's design, not building as the initial mechanism.
- **Reviewer/implementer separation.** `reviewer.md`'s existing constraint (no source edits, only `last_reviewed` frontmatter) is the load-bearing precedent for keeping a browser-verifier delegate from also being a browser-fixer delegate. If the plugin wants a "fixer" persona at all (e.g., wrapping Playwright's Healer for locator repair), it should be a distinct, narrowly-scoped agent definition, not a capability bolted onto the verifier.

## Recommendations (reference for `/propose-revise`, not decisions)

1. **Default the plugin to in-harness subagent delegation**, sonnet-tier, as the loop-holder for browser driving; opus/fable dispatches and reads summaries, never drives the browser directly. This is the highest-leverage, lowest-complexity option and requires no new protocol.
2. **Evaluate the first-party browser-use tool (`computer_toolset_20260801`'s sibling) as the default capture/driving leg**, specifically to retire the version-pinning failure class weftwise has hit three times in 2026. Confirm runtime availability inside the target harness/devcontainer before committing — this is the single open item most likely to gate adoption.
3. **Keep chrome-devtools-mcp and/or Playwright MCP as complements, not the default**, for cases needing network/performance traces or deterministic selector-based test authoring that the browser-use tool does not cover.
4. **Reuse the existing R1-R6 visual-review discipline verbatim as the verdict layer**; do not reinvent a "does this look right" judge inside this new plugin. The plugin's contribution is upstream (getting pixels cheaply), not downstream (judging them).
5. **Treat A2A as a documented future escalation, not the initial architecture**, gated on an actual cross-harness/cross-org need; default to the durable-specialist pattern for same-org session reuse.
6. **Split "verifier" and "fixer" personas if a fixer is built at all**, preserving the reviewer-never-edits-source separation; scope any fixer narrowly (e.g., locator repair via Playwright's Healer) rather than granting a browser delegate general UI-code-editing authority.
7. **Primary-verify the Playwright Planner/Generator/Healer integration claims** (exact CLI shape, the reported `claude` integration mode) against Playwright's own docs before the proposal specifies concrete wiring — this report's sourcing for that item is search-only, not primary-fetched.

## Open Questions for the Proposal

- Which toolset(s) does the plugin wire up by default, and does that choice vary by target harness (Claude Code vs OpenCode) or by whether a devcontainer/pinned-binary environment is even in play?
- Is a fixer persona in scope for v1 at all, or does "minor UI tweaking" stay entirely inside the existing implement/review loop for this plugin's first cut?
- What is the concrete latency/round-trip budget past which a delegate stops being cheaper than the lead just looking itself (relevant once Report B's parallelization findings land)?
- Does the plugin need any A2A surface in v1, or is that genuinely deferred until a real cross-harness use case appears?
- How does this plugin's delegate agent definition relate to the existing `reviewer` agent — a new agent type, or an additive capability on an existing one?
