# Verifying time-based UI behavior: deterministic introspection vs perceptual judgment

> BLUF: a single screenshot is a static-end-state artifact and proves nothing about motion, but the gap is not actually unclosed.
> A layered set of techniques exists, ordered cheap-to-expensive: deterministic, non-visual introspection (`getAnimations()`, transition/animation DOM events) proves an animation object existed and completed for near-zero cost; Playwright's `page.clock` makes sampling a specific animation frame byte-for-byte reproducible; frame-interval capture (screenshots, `recordVideo`, trace-viewer screencast) turns motion into an artifact a human or a model can look at; and VLM/video-model judgment is the only layer that can answer "did it look right," at real cost and with no determinism guarantee.
> The headline recommendation: reach for deterministic introspection first for any page-transition or drag-state check (it answers "did it run" cheaply and reliably), reserve frame-diffing and Playwright's `animations:'disabled'` screenshot option for the opposite, complementary need (respectively: cheap motion smoke-tests, and stable end-state regression baselines), and only escalate to a VLM/video model when the open question is genuinely perceptual (did the easing look right, did it slide from the correct side) rather than "did a transition fire."
> This extends [the 2026-08-05 visual-verification survey](2026-08-05-visual-verification-skills-web-survey.md)'s finding that "the market sells regression, not correctness": for motion specifically, the market barely sells anything at all, deterministic introspection is the one place cdocs can get an objective, non-perceptual answer that the static-screenshot case never had, and should prefer it whenever the underlying question is presence/completion rather than aesthetics.

## Context / Background

Two prior reports in this task list establish who should drive a browser delegate and how a fresh looker judges a static render against a design reference: [browser-delegation-approaches](2026-09-17-browser-delegation-approaches.md) (architecture, model tiering) and [delegate-model-comparison](2026-09-17-delegate-model-comparison.md) (which models to use for driving vs verdict).
Neither addresses a question that comes up whenever a delegate is asked to verify something that happens over time rather than a fixed pixel state: a drawer sliding in, a drag-reorder showing an intermediate drag position, a hover transition, a loading spinner, a video actually playing.
A screenshot taken after the fact shows only the end state, so an agent that only screenshots cannot distinguish "the drawer slid in over 300ms" from "the drawer teleported in with no transition at all."

This report surveys what closes that gap, split into the same deterministic-vs-perceptual axis the visual-verification survey already used for static renders, extended for the time dimension.
It is written as an infrequent-use reference, not a workflow to adopt by default: most UI verification in cdocs stays static-screenshot-plus-VLM-looker per the existing discipline, and the techniques below are for the specific, occasional case where "did it animate" is the actual open question.

## Key Findings

- **The Web Animations API gives a free, deterministic existence check that most agents skip.** `document.getAnimations()` and `element.getAnimations()` (MDN, primary-verified) return every in-flight CSS animation, CSS transition, and Web Animations API animation as `Animation` objects exposing `playState`, `effect`, `timing`, and `currentTime`. A one-line `page.evaluate(() => document.getAnimations().some(a => a.playState === 'running'))` (or a locator-scoped `element.getAnimations()`) answers "is something animating right now" without a single pixel captured. This is the cheapest, most reliable rung on the ladder, and it is not a screenshot substitute; it says an `Animation` object exists, not that it painted correctly.
- **Transition and animation DOM events prove a specific run happened, and their firing order is exact and easy to get wrong.** Per MDN (primary-verified, [`transitionend`](https://developer.mozilla.org/en-US/docs/Web/API/Element/transitionend_event)): `transitionrun` fires when the transition is created (before any delay), `transitionstart` fires once the delay has elapsed and the transition begins, `transitionend` fires on completion, and `transitioncancel` fires if it is interrupted, in which case `transitionend` does **not** fire. `transitionend` will also not fire at all if `transition-duration` and `transition-delay` are both `0s` or undeclared. The `animationstart`/`animationiteration`/`animationend`/`animationcancel` family mirrors this for `@keyframes` animations. A test that listens only for `transitionend` and treats its absence as "no transition happened" is wrong if the transition was legitimately canceled (`transitioncancel` fired instead) or if the developer accidentally shipped a `transition-duration: 0`.
- **`prefers-reduced-motion` is a live correctness hazard for exactly this class of assertion, not just an accessibility nicety.** CI containers and headless browser defaults can carry `prefers-reduced-motion: reduce`, and well-behaved apps intentionally skip or shorten animations under that setting. An assertion that expects `getAnimations()` to return a running animation, or expects a `transitionrun` event, can fail correctly (the app is behaving as designed) in an environment where the preference is set, which looks identical to a real regression from the outside. Any animation-presence test should either force `prefers-reduced-motion: no-preference` for the run (Playwright: `page.emulateMedia({ reducedMotion: 'no-preference' })`) or explicitly branch the assertion on the media query's state, mirroring the app's own branching.
- **Sampling computed styles across `requestAnimationFrame` ticks is the fallback for animations that don't use the Web Animations API at all.** An imperative animation driven by a hand-rolled `requestAnimationFrame` loop that mutates `style.transform` directly never creates an `Animation` object and never fires transition/animation events, so `getAnimations()` returns nothing for it. The only introspection left is polling `getComputedStyle(el).transform` (or whichever property) across a few rAF ticks and asserting the value differs between samples, i.e., proving mid-interpolation rather than a jump from start value straight to end value. This is noisier (frame timing varies by environment) and proves less (a value changed, not that the intended animation ran), but it is the only deterministic option when a codebase bypasses the standard animation primitives.
- **Playwright's `page.clock` makes animation-frame sampling reproducible, and it must be installed before any timers fire.** Per Playwright's own docs (primary-verified, `playwright.dev/docs/clock`): `clock.install(options?)` initializes the clock and overrides `Date`, `setTimeout`/`clearTimeout`, `setInterval`/`clearInterval`, `requestAnimationFrame`/`cancelAnimationFrame`, `requestIdleCallback`/`cancelIdleCallback`, `performance`, and `Event.timeStamp`; `pauseAt(date)` halts time at a moment; `fastForward(duration)` jumps time and fires all due timers/animation frames at once; `runFor(ms)` ticks through time incrementally, firing timers and rAF callbacks along the way, which is the method that actually lets you land on and screenshot a specific mid-animation frame; `resume()` un-pauses; `setFixedTime`/`setSystemTime` control wall-clock time separately from timer progression. The docs are explicit that `install()` must be the first clock call in a test, and that calling any clock method before it is undefined behavior. This turns "screenshot the drawer at t=150ms of its 300ms transition" from a flaky `await page.waitForTimeout(150)` race into a deterministic, repeatable frame pick, at the cost of the animation running on Playwright's simulated clock rather than the browser's real compositor thread (a CSS animation driven by the compositor, not `requestAnimationFrame`, may not be perfectly steppable this way; verify against the specific animation's implementation before relying on exact intermediate values).
- **`animations: 'disabled'` on `page.screenshot()`/`toHaveScreenshot()` solves the opposite problem and must not be confused with a motion-verification tool.** Per Playwright's source docs (primary-verified via the upstream `params.md`): with `animations: 'disabled'`, "finite animations are fast-forwarded to completion, so they'll fire `transitionend` event[s]," and "infinite animations are canceled to initial state, and then played over after the screenshot." This exists to make a screenshot **stable** for baseline diffing (`toHaveScreenshot`), by deliberately erasing in-flight motion so two runs of the same test produce byte-identical pixels regardless of animation timing jitter. It is the correct tool when the goal is "assert this static layout didn't regress" and actively the wrong tool when the goal is "prove this thing animated" — using it in a motion test would guarantee the very absence of motion the test is supposed to detect. It covers CSS animations, CSS transitions, and Web Animations; based on the mechanism described, it has no defined effect on an imperative `requestAnimationFrame` loop that isn't registered as a `CSSAnimation`/`CSSTransition`/`Animation` object, so hand-rolled JS animations may still leak timing nondeterminism into a "stable" screenshot (reasoned from the documented mechanism, not independently confirmed against a specific edge-case test in this pass).
- **`recordVideo` finalizes only after the browser context closes, so it is a post-hoc artifact, not something you can gate a mid-test assertion on.** Per Playwright's docs (primary-verified): video is written on context closure; `page.video().path()` is only available after the context/page closes. It is the right tool for a debugging or CI artifact (or as the input to a video-capable VLM, see below), and the wrong tool for "assert mid-test that the drawer is currently sliding," which needs one of the introspection or interval-screenshot techniques instead.
- **The trace viewer's screencast is a scrubbable timeline for human debugging; its exact capture cadence and any programmatic per-frame extraction from `trace.zip` were not confirmed in this pass.** Playwright's own trace-viewer docs describe stepping "back and forward through each action" and inspecting a live DOM snapshot per action, but the granularity of the underlying screencast frames (continuous sampling vs. per-action only) and any supported CLI/API for pulling individual frames out of a saved trace were not found in the fetched documentation. Treat this as a human-facing debugging aid to open in `npx playwright show-trace`, not (without further verification) a source of frames to feed a VLM programmatically.
- **A raw screenshot-diff between two timed captures is a cheap, model-free motion smoke-test, distinct from both introspection and VLM judgment.** Taking screenshots at, e.g., t=0ms and t=150ms of a transition and running them through the same pixel-differ the static-verification discipline already uses (`compare -metric AE`, `pixelmatch`, `odiff`, per the [2026-08-05 survey](2026-08-05-visual-verification-skills-web-survey.md)) proves "something visually changed between these two moments," for the cost of one extra screenshot and an existing tool. It cannot say what changed, cannot rule out an unrelated repaint (a blinking cursor, a hover state elsewhere on the page) causing a false positive, and says nothing about whether the *right* animation happened, but it is a strictly cheaper gate than a VLM call and a good pre-filter before escalating.
- **Claude's vision input has no native video ingestion; the documented alternative is an ordered sequence of labeled still images in one request.** Per `platform.claude.com/docs/en/build-with-claude/vision` (primary-verified, fetched 2026-09-18): Claude accepts JPEG/PNG/GIF/WebP images and explicitly states "Animations are unsupported, and only the first frame is used" for animated GIFs. There is no video content-block type. The documented pattern for a sequence is multiple `image` blocks in one message, each preceded by a short text label (`Image 1:`, `Image 2:`), which Claude "analyzes jointly" — this is the mechanism to hand a delegate three or four timed screenshots of a drawer animation and ask "does this look like the drawer slides in from the left across these frames," and it is exactly the ordered-frame-sequence technique this report was asked to verify. Request limits: up to 100 images per API request on 200k-context models (600 on others), each image separately token-costed by resolution.
- **Gemini does accept native video input, but its default frame-sampling rate under-samples a short UI clip.** Per `ai.google.dev/gemini-api/docs/video-understanding` (verified): the API accepts uploaded video files or inline data across common formats, "all Gemini models can process video data," and the default extraction is 1 frame per second. A 1-2 second recording of a drawer sliding in would yield only one or two sampled frames at that default, likely missing the motion entirely; the docs note an `fps` parameter to raise the sampling rate for short, detail-dense clips, which must be set explicitly for this use case rather than relied on as a default. Token cost scales with video duration and sampling rate (roughly 100 tokens/second at default resolution, ~300/second at high resolution), so a longer or over-sampled clip is not free.
- **OpenAI's vision API, like Claude's, has no native video content type; it is images-only, with animated GIFs explicitly excluded.** Per `developers.openai.com/api/docs/guides/images` (fetched via redirect from `platform.openai.com/docs/guides/vision`, verified): supported inputs are PNG/JPEG/WEBP/non-animated GIF, and up to 1,500 images can be submitted in one request. Motion must be represented the same way as for Claude: extracted frames submitted as an ordered sequence of stills.
- **chrome-devtools-mcp's tool list has a `performance_start_trace`/`performance_stop_trace`/`performance_analyze_insight` triplet and `take_screenshot`, but no dedicated "did this animate" tool.** Per the project's own tool reference (primary-verified via GitHub): the performance tools produce Chrome performance traces and named "insights," which can surface frame-timing/jank information, but the reference lists no animation-specific inspection tool. Getting an `Animation`-object-level answer through chrome-devtools-mcp today means falling back to its `evaluate_script` tool to run the same `getAnimations()` call described above; the MCP server does not expose that primitive as a first-class tool name.
- **The Chrome DevTools Animations panel is a rich manual-inspection UI, not (as documented) a scriptable automation surface.** Per `developer.chrome.com/docs/devtools/css/animations` (verified): it captures CSS animations, CSS transitions, Web Animations, and View Transitions on a scrubbable timeline with playhead dragging, speed controls, and keyframe editing. The fetched documentation is UI-only and does not describe DevTools-protocol integration for the panel itself.
- **The underlying Chrome DevTools Protocol does expose a programmatic `Animation` domain, independent of the manual panel, but it is not surfaced by chrome-devtools-mcp's current tool list.** Per `chromedevtools.github.io/devtools-protocol` (verified): the CDP `Animation` domain fires `animationCreated`/`animationStarted`/`animationCanceled` events and exposes `getCurrentTime`, `setPlaybackRate`, `seekAnimations`, and `releaseAnimations` methods, which is a genuine low-level automation primitive for detecting and controlling animations from a script. Using it today would require a raw CDP session (e.g., from a Puppeteer- or Playwright-driven script) rather than an off-the-shelf MCP tool call; it is a real capability that nothing surveyed here wraps as a named tool.
- **Simulating a drag-intermediate state is straightforward with Playwright's low-level mouse API, with one concrete, documented gotcha.** `locator.dragTo()` performs hover, `mouse.down()`, move, `mouse.up()` in one call and is the high-level default; for capturing an actual intermediate frame, the manual sequence (`hover()` → `mouse.down()` → `mouse.move(x, y, { steps: n })` → screenshot → `mouse.up()`) is required, since `dragTo()` does not expose a mid-drag hook. Playwright's `mouse.move(x, y, options)` (primary-verified) defaults `steps` to `1`, meaning a single jump with no interpolated `mousemove` events unless `steps` is raised; Playwright's own input-actions docs carry the specific, load-bearing caveat that "if your page relies on the `dragover` event being dispatched, you need at least two mouse moves to trigger it in all browsers." A drag-reorder implemented against `dragover` (common for HTML5 native drag-and-drop) will silently never show its intermediate drag-state UI in a test that does a single `mouse.move` — this is a documented, easy-to-hit trap distinct from the general "screenshot mid-drag" idea.
- **No survey source describes a productized "does this animate correctly" tool analogous to Applitools for static renders.** Consistent with [the 2026-08-05 survey](2026-08-05-visual-verification-skills-web-survey.md)'s conclusion that the visual-regression market sells "diff against your own history," nothing found here sells "diff this recorded motion against a reference motion" either; Applitools' visual-AI marketing does not claim motion-aware comparison in the sources checked. The judgment layer for motion is, if anything, even more clearly cdocs' own to own than the static case, because there is not even a baseline-diff product to point at as a lesser alternative.

## Technique comparison

| Technique | Deterministic or perceptual | What it proves | What it cannot prove | Relative cost | Reliability / flakiness risk |
|---|---|---|---|---|---|
| `getAnimations()` / `playState` | Deterministic | An `Animation` object exists and its play state (running/paused/finished) | Correct visual appearance; misses non-WAAPI imperative animations | Near-zero (one `evaluate`) | High, if the check runs while the animation is actually in-flight; races if fired too late |
| Transition/animation DOM events | Deterministic | A transition/animation of a specific kind actually ran (or was canceled) | Correct visual result; absence can be a false negative under `prefers-reduced-motion` or `duration: 0` | Low | High if listener attached before trigger; brittle to fast/short-duration transitions |
| rAF computed-style sampling | Deterministic (noisier) | A styled property is mid-interpolation, not just start/end | Which animation, or whether it's the intended one; noisy timing | Low-moderate | Moderate; frame timing varies across CI/headless environments |
| `page.clock` frame sampling | Deterministic, reproducible | Exact DOM/style state at a chosen simulated time offset | "Smoothness" or real compositor-thread behavior for compositor-driven animations | Low-moderate | Highest of any technique, by design; must be installed before triggering |
| `animations: 'disabled'` screenshot | Deterministic (inverse use) | A stable, motion-free end-state screenshot for baseline diffing | Nothing about motion; actively removes the evidence a motion test needs | Low | Very high for its actual purpose; wrong tool if misapplied to a motion test |
| Interval screenshot diffing | Deterministic pixel-diff, no model | Two captures differ, i.e. some visual change occurred in the window | What changed, or whether it's the intended animation (false positives from unrelated repaints) | Low-moderate | Moderate; needs stable capture cadence |
| `recordVideo` | Capture only, needs review | A full video artifact of the run exists, for later human or VLM review | Nothing on its own; finalizes only after context close, so no mid-test gating | Moderate (encoding overhead) | Reliable as an artifact; coarse-grained, not for in-test assertions |
| Trace-viewer screencast | Capture only, needs review | A scrubbable timeline for human debugging | Programmatic per-frame extraction and exact capture cadence, unconfirmed in this pass | Moderate | Good for humans; unverified fit for automated agent use |
| Ordered-frame VLM judgment (Claude, GPT-4o/5) | Perceptual | A holistic "did this look like it slid in from the left" judgment across labeled stills | Motion between the sampled instants (frame-gap blindness); no native video for either vendor | High (tokens, per image, judgment non-determinism) | Needs ensemble/ freshness discipline per existing cdocs practice; sampling choice biases the verdict |
| Native video VLM judgment (Gemini) | Perceptual | A holistic judgment from an actual video clip, not discrete stills | Anything faster than the configured `fps`; defaults (1 fps) undersample a 1-2s UI clip | Moderate-high | Must explicitly raise `fps` for short clips; still non-deterministic |
| CDP `Animation` domain (raw) | Deterministic, low-level | Animation lifecycle events and programmatic seek/playback control | Not exposed as a named tool in chrome-devtools-mcp today; needs a raw CDP bridge | Low if wired, but not off-the-shelf | Powerful but unproductized for this surface |

## Recommendations

1. **Default to deterministic introspection first for any "did it animate" question.** `getAnimations()`/`playState` and the transition/animation event family answer "did this run" for near-zero cost and without a model in the loop; use them whenever the open question is presence or completion rather than aesthetics. This mirrors the existing cdocs posture (own the judgment, prefer commodity/cheap primitives where they give an objective answer) and is a stronger fit here than for static rendering, because motion has an objective, non-perceptual signal (an `Animation` object, a fired event) that static layout never had.
2. **Force or account for `prefers-reduced-motion` explicitly in any animation-presence test.** Set `page.emulateMedia({ reducedMotion: 'no-preference' })` (Playwright) before asserting an animation ran, or branch the assertion the same way the app does, so a correctly-reduced-motion environment does not read as a false regression.
3. **Use `page.clock` when the check needs a specific, reproducible mid-animation frame** (e.g., "the drawer is 50% translated at t=150ms"), not `page.waitForTimeout` racing against real time. Verify against the specific animation's implementation (compositor-driven vs. rAF-driven) before trusting exact intermediate values, since the clock's guarantees are strongest for timer/rAF-driven JS animation, weaker for pure CSS/compositor animation.
4. **Never use `animations: 'disabled'` to test that something animates; use it only for stable-baseline regression screenshots.** These are opposite needs from the same option, and conflating them silently defeats a motion test rather than failing loudly.
5. **Escalate to VLM/video-model judgment only for genuinely perceptual questions** (did the easing look natural, did it visibly come from the correct side, does a spinner read as "loading" rather than "broken"), and prefer Claude's or GPT's ordered-labeled-image-sequence pattern over Gemini's native video path unless the clip is long enough or `fps` is deliberately raised to avoid under-sampling; either way, treat the verdict as needing the same freshness/ensemble discipline the static VLM-looker already uses, not a one-shot oracle.
6. **For drag-state and reorder checks, always parameterize `mouse.move`'s `steps` above its default of 1**, and specifically use at least two moves if the target implementation listens for native `dragover` — this is a documented, concrete failure mode (the intermediate drag UI silently never renders in the test) distinct from generic screenshot timing.
7. **Route the cheap, deterministic legs of this work through the sonnet-tier delegate described in the [browser-delegation-approaches](2026-09-17-browser-delegation-approaches.md) report**, reserving opus-class judgment for the VLM/video-model escalation step, consistent with that report's model-tiering split (driving and capture cheap, verdict expensive).
8. **If a CDP-level animation primitive becomes worth adopting** (e.g., programmatically seeking an animation to an exact point rather than relying on `page.clock`'s timer emulation), treat the CDP `Animation` domain as the concrete mechanism to bridge in via `evaluate_script`/a raw CDP session, since it is not currently exposed as a named chrome-devtools-mcp tool.

## Biggest reliability gaps

- **Trace-viewer screencast granularity and programmatic frame extraction are unverified.** If a future workflow wants to pull exact frames from a saved `trace.zip` for VLM review, this needs a dedicated verification pass against Playwright's trace format, not the documentation surface checked here.
- **`page.clock`'s interaction with compositor-driven (as opposed to `requestAnimationFrame`-driven) CSS animations is not confirmed either way.** The clock overrides JS-visible timing primitives; whether that reliably steps a pure-CSS animation running on the compositor thread to an exact intermediate frame was reasoned from the documented override list, not independently tested.
- **Gemini's actual behavior on a real 1-2 second UI clip at a raised `fps`** (does it reliably catch a fast drawer slide, or does encoding/compression still blur the motion) was not empirically tested in this pass; the finding here is limited to the documented default-sampling gap, not a measured false-negative rate.
- **No model in this survey has been benchmarked specifically on "did this UI element animate correctly,"** as distinct from the MT-Web2Code-style static-defect-repair benchmarks already covered in [delegate-model-comparison](2026-09-17-delegate-model-comparison.md); any recommendation to route motion verdicts to a specific model tier is an extrapolation from general vision/video capability, not a task-matched benchmark result.
