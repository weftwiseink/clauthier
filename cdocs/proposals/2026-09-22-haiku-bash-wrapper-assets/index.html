Haiku Bash-Output Wrapper

cdocs:bash-runner + a deterministic output floor, and how two rounds of live testing overturned three of the proposal's own assumptions before it shipped.

Ship two mechanisms together, not one: a haiku-tier cdocs:bash-runner agent (opt-in, captures a command's output to its own scratch file, extracts a salient excerpt) for anticipated-verbose calls, plus a tightened bashOutputMaxChars settings floor (start 6,000 chars, band 4,000–8,000) for everything nobody thought to route through the wrapper.

Both hook-based interception routes were investigated and both stay deferred — one because it is genuinely dead on this platform version, one because live testing found it actually works but doesn't close a real gap. Read the corrections below: this proposal's headline finding is procedural as much as technical — reading a GitHub issue is not verification, only a reproducible live canary is, and this repo hit that lesson twice in two rounds.

1 · The problem, sized

Bash command output is 28.5% of all read intake across a measured week of this project's own sessions — 3.76M of 13.17M approx-tokens, from 9,581 results averaging 390 tokens each. cdocs/reports/2026-09-20-read-source-attribution.md called this "death by a thousand cuts": no single whale result, just volume.

2 · Two rounds, two live-tested corrections

The proposal's first draft reasoned about platform hook behavior from GitHub issue text. Both live-tested corrections below tightened the design, they didn't loosen it — and the pattern (issue-reading is not verification) repeats across this session's other proposals, not just this one.

2a · "Both hooks are dead" → one is, one isn't

Claimed (round 1 draft, from issue text)

Both channels inert for Bash

PostToolUse updatedToolOutput and PreToolUse updatedInput both silently no-op for the built-in Bash tool, citing #68951 and #79321 as closed "not planned."

Verified (round 1, live canary, 2/2 runs, CC 2.1.280 Linux headless)

Only one channel is actually dead

PreToolUse updatedInput rewrote the command — transcript showed the model's original request, but the tool result was the rewritten text. PostToolUse updatedToolOutput fired but the sentinel never reached the model: genuinely inert.

$ echo ORIGINAL_OUTPUT # PreToolUse hook rewrites to: echo REWRITE_APPLIED tool_use.input.command = "echo ORIGINAL_OUTPUT" ← model's request, unchanged toolUseResult.stdout = "REWRITE_APPLIED" ← rewrite executed

#79321 was filed against 2.1.215 on Windows desktop; this canary ran 2.1.280 on Linux headless. The behavior is environment-dependent, not a fixed platform fact — the proposal now gates any future use of this channel on re-running the canary, never on trusting the issue's status.

2b · "The cap truncates" → the cap spills to a file

Claimed (round 1 draft)

Head/tail clip at the ceiling

A command over the bashOutputMaxChars ceiling gets cut to a head+tail excerpt, like the wrapper's own extraction logic — so the wrapper and the cap were modeled as doing the same thing at different thresholds.

Verified (round 1, direct observation + CC docs)

A cliff, not a clip — and it depends on exit status

A valid (exit 0) over-ceiling result collapses to a file path + ~2,000-char preview. Only a failed command gets the lossy head+tail excerpt, with no file at all — the middle is unrecoverable without a re-run.

3 · The wrapper's own self-defeating bug

Because cdocs:bash-runner is itself Bash-only, its own dispatched command hits the exact same ceiling described above. The original design — "the haiku agent reads the whole output once in disposable context" — would have failed its own containment test: a seq 1 200000 canary would spill to a ~2k preview inside the runner, and a Bash-only agent asked for "the last line" could not recover it from a preview.

Before · read-once (broken)

<cmd> runs directly, its stdout is the runner's tool result. Under the cap, this is fine. Over the cap, the runner's own tool result is a truncated preview — the exact failure mode the runner exists to prevent, now happening to the runner itself.

After · capture-to-file-then-extract

Redirect to a scratch file, echo the exit code as the only tool result, then run bounded grep/tail/head/cut over the file. Every step's own output stays small by construction.

OUT="$SCRATCH/bash-runner-$(date +%s).log" <cmd> > "$OUT" 2>&1; echo "exit=$?" # tool result: just "exit=<n>" — tiny, always exit 0 grep -nE '<pattern>' "$OUT" | head -n N # bounded extraction, cannot itself spill tail -n N "$OUT" # ...

Because the trailing echo "exit=$?" is the last command in the pipeline, the overall invocation always reports exit 0 with a tiny result — regardless of what <cmd> itself did. That sidesteps the lossy failure-path excerpt from §2b entirely: the full output is always on disk, for every command the runner ever captures.

Round-2 reviewer's own verification (not trusted from prose)

seq 1 200000 > "$OUT" 2>&1; echo "exit=$?" → exit=0 # entire capture-step tool result wc -c "$OUT" → 1288895 # 1.3MB, on disk tail -n 1 "$OUT" → 200000 # true last line, recovered

When to dispatch cdocs:bash-runner

Reordered in round 1 from intuition (build logs first) to the corpus's actual observed traffic — the 15 heaviest results (22–29k chars each) are all sweeps, not builds:

grep -rn sweepsfindgit diffmulti-file cat loopsbuild logstest suitesnpm installlintersterraform plan/applycontainer buildsgit log -pany unbounded/unfamiliar command

Salience specs come in two shapes: line-oriented for pass/fail commands ("return the exit code and any line matching error/fail"), and aggregate for sweeps where the matches themselves are the signal ("matches per file, first 3 per file") — a head/tail default would be the wrong shape for a sweep.

5 · Build vs. adopt: why not rtk

A parallel report investigated whether existing tooling could replace the bespoke build. rtk-ai/rtk is real and relevant: Apache-2.0, Rust, 81.5k stars, and it already deterministically compresses 100+ known dev commands — including exactly the grep/find/git diff/cat-sweep shapes that dominate this corpus's whale traffic.

What rtk has

Fast, free, deterministic compression for ~100 known command types. Zero LLM cost. Already covers the sweep patterns this proposal's own data shows are the heaviest traffic.

What rtk structurally lacks

No caller-steerable salience spec. No coverage of unfamiliar/unanticipated commands — they pass through unfiltered. No semantic "find the buried needle regardless of format." These are cdocs:bash-runner's entire value proposition.

The rejected hybrid: bash-runner shells out to rtk as a pre-filter

Considered explicitly, rejected on architectural grounds sharper than a simple dependency-hygiene concern:

  • Semantic incompatibility on exactly the whale traffic. rtk's compression is fixed per command type, applied before the caller's salience spec ever sees the output. A caller asking for "matches per file, first 3 per file" over a grep sweep may find rtk has already dropped or reshaped precisely what was asked for — the pre-filter and the semantic extractor fight hardest on the case where "the matches ARE the signal."
  • Breaks the no-silent-loss guarantee §3 depends on. The containment argument rests on the runner controlling the exact bytes on disk. Insert rtk and the on-disk artifact is already rtk-transformed — recovering the true raw output would require capturing twice.
  • Environment availability. rtk is pre-1.0 (dev-0.50.0-rc.451), CLI-only with no library/MCP mode, and would need to be installed and PATH-resolvable in every consuming environment — including CI and sandboxes the plugin cannot provision.

One capability needs no design change at all: a caller who wants rtk's compression can already dispatch rtk git diff as the command itself — the runner just captures whatever it's given. rtk is cited in mechanism 3's background as further evidence for staying deferred (a mature tool already covers that allowlist's territory better than a bespoke one would), not adopted as a dependency.

6 · Tiering

Where this sits in model-tiering.md

cdocs:bash-runner joins nit-fix as a named example in the Mechanical / Deterministic Fan-Out Tier (haiku) — tasks with a clear pass/fail signal and no need for reasoning flexibility, where a stronger model buys nothing. This is documented as a named carve-out, not an automatic override: per the rule's Precedence section, a consumer with a blanket opus floor still has to explicitly bless this dispatch down to haiku — the shape ships ready to adopt, it doesn't silently downgrade anyone's existing policy.
