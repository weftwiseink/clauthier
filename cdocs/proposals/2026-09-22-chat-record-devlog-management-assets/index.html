Chat Record, Scratchpoint & Devlog Splitting

How the design works: what one turn writes, the record format, the script and its two hooks, how the record stays top-level only, the resumption guidance and the compaction text it replaces, the Scratchpoint, the split rule, and the phase plan.

Three artifacts, each with one job. A per-session chat record holds your prompts verbatim and at least one short gist bullet from the agent for every turn you start, each turn closed by a -- <session> at <time> sign-off. A Scratchpoint in the devlog holds current state, replaced in place by the devlog's owner. Devlog chunks split a long devlog where a concern has closed.

The mechanism is small: two hooks (UserPromptSubmit, Stop) and one script on the agent's PATH (chat-record), all Claude Code only. The session id ties a record together and the order of its lines delimits turns. A devlog lists its records in chat_record: frontmatter. Nothing runs until /cdocs:init creates cdocs/_chat/.

Compaction is left to you and the harness. The record knows nothing about it, no agent schedules it or estimates its own context, and cdocs' older instructions that did are removed. What to re-read after a compaction is rule text.

The record path comes from the session id: the hooks read it from their payload, and the agent's Bash has it as CLAUDE_CODE_SESSION_ID. The file is found by the glob cdocs/_chat/*-<session_id>.md, so --resume on a later day appends to the same file. If one session's record was started in two checkouts on different days, every mode uses the earliest-dated match.

  • Activation. The script walks up from the working directory to the git toplevel, stopping at the first cdocs/, and never looks above the toplevel. It records only if that cdocs/_chat/ exists, which /cdocs:init creates along with the rule text. A project that hasn't opted in, and any directory outside a git work tree, records nothing and is never blocked.
  • Claude Code only. Hooks and bin/ are not ported, so OpenCode and AGENTS.md readers keep no record; the per-turn rule reaches them through init but its scope sentence makes it inert. Resumption there reads the devlog's Scratchpoint and latest handoff.

A devlog names the records of every session that worked on it in an optional frontmatter list. It is a list because a devlog outlives sessions, and frontmatter because it stays with the root when a devlog splits. The devlogs for a record are grep -l '<record path>' cdocs/devlogs/*.md; a session that works on several devlogs, as an oversee arc does, is listed in each.

chat_record: - cdocs/_chat/2026-10-05-3f2a9c1e-....md
  • Commits. The top-level session stages its record by explicit path whenever it commits a devlog that lists it: at each handoff in a loop, and with any devlog commit in a plain session. A session that never works on a devlog leaves its record untracked. Dispatched agents never stage cdocs/_chat/.
  • Merges. /cdocs:init scaffolds cdocs/_chat/.gitattributes with *.md merge=union, so appends made to one record in a worktree and in main merge or rebase without conflict, including two checkouts that each created the same record.

2One turn

A turn you start writes your prompt, at least one agent bullet, and a sign-off. The Stop hook reads only the record's last marker line (a header or a sign-off); it never reads or judges content. If the last marker is still your @user, no note was written, so it blocks once, and the second Stop always lets the turn end. In plan mode, where the harness forbids writes, it signs off without blocking.

3Record format

A record is a sequence of blocks. Only real speakers get an @ header; the hook is not a speaker, so the turn's end time is a sign-off line after the agent's block rather than a block of its own. Headers and sign-offs are the record's markers, and their order alone delimits turns.

@user: 2026-10-05T10:45:12-07:00 lets make chat record path frontmatter attribute instead of a section maybe? @opus-5-5: 2026-10-05T10:46:40-07:00 - gist: seven simplification steers sent to a fresh round-9 proposer; artifact update after accept -- clauth-opt-context at 2026-10-05T10:46:44-07:00 @user: 2026-10-05T10:58:03-07:00 runner tmp: yeah that deletion seems fine @opus-5-5: 2026-10-05T10:59:10-07:00 - gist: runner captures older than ~24h are pruned before each run (552684d); exit code preserved - follow-up: plugin version bump and OpenCode republish still pending -- clauth-opt-context at 2026-10-05T10:59:15-07:00

illustrative excerpt in the proposal's grammar, built from this arc's own turns

  • hook@userwritten by UserPromptSubmit at submission time, prompt verbatim. Harness envelopes (a prompt opening with <task-notification or <system-reminder) are not recorded; a background agent's result is reflected in the agent's own note when it matters.
  • agent@<model-short>written by chat-record note --as <model-short>; the script adds the timestamp. The agent supplies the model name, since no hook payload carries one; without --as the speaker is assistant. The value is mapped to [A-Za-z0-9._-] (opus-4-6[1m] becomes opus-4-6-1m-) and must then match the header pattern and not be user in any case, or note exits non-zero and writes nothing. A malformed speaker can neither glue a note into the prompt above it nor forge a human header.
  • hook-- <session> at <ts>written by Stop. The session token is the /rename title (the last custom-title line in the transcript), mapped to [A-Za-z0-9._-], else the first 8 hex of the session id. Timestamps are ISO 8601 with a colon offset, produced portably on GNU and BSD date. A turn's duration is its @user time to its sign-off.
PatternRegex
header^@[A-Za-z0-9][A-Za-z0-9._-]*: then an optional <timestamp>
sign-off^-- [A-Za-z0-9._-]+ at <ISO-8601 with offset>$
bodyany line matching neither; a body line that looks like either gets one leading backslash, stripped on read

Gist bullets

At least one bullet per turn you start; aim for one to three, one line each, under about 120 characters. The test for a bullet: would a successor reading only the prompts and these bullets know where things stand?

gist: (default)

what the turn concluded, decided or changed

query:

a search that proved useful and what it found

read:

a high-salience file and why it mattered

follow-up:

an open thread to come back to

This is a guideline, not a prohibition list. Don't log every commit, test run, edit or tool output, and don't paste the reply. A commit that closes a long thread, or a test result that changes the plan, can be the turn's gist. The shape to avoid is the enumerated log (- edited X - ran tests - committed abc); the shape to produce is the one-line state of play.

Slash commands are recorded as the raw invocation string. Built-in commands (/compact, /clear, /model, /effort, /rename and the like) fire no UserPromptSubmit and leave no trace.

4The script and its hooks

plugins/cdocs/bin/chat-record is Bash plus jq. A plugin's bin/ is on the Bash tool's PATH while the plugin is enabled, so the agent runs it as a bare command.

ModeInvocationBehavior
hookchat-record UserPromptSubmitappend @user for a human prompt; skip harness envelopes; never blocks
hookchat-record Stopsign-off, block once, or nothing (table below)
agentchat-record note [--as m], bullets on stdinappend @<m>: <now> and the body
agentchat-record pathprint the record path relative to the git toplevel (cdocs/_chat/...), the form chat_record: takes; never creates the file

The note body comes only from stdin, written as a quoted heredoc, which does no shell expansion. A double-quoted argument would execute backticks and $(...), and a single-quoted one breaks on apostrophes.

chat-record note --as opus-5-5 <<'EOF' - query: `rg -n "stop_hook_active"` found the one-shot guard; didn't need the binary EOF
Last markerWritesEmits
an agent header (a note since the turn began)sign-offnothing

@user, with stop_hook_active or permission_mode: plansign-offnothing
a sign-off, or none (a turn you did not start, with no note)nothingnothing
  • Hook mode exits silently (exit 0, no write, no block) when the payload carries agent_id, CDOCS_CHAT_RECORD=off, jq or git is missing, activation finds no cdocs/_chat/, or (for Stop) no record exists. It always exits 0 and writes errors to stderr only.
  • Stdout stays empty in hook mode except for the Stop block JSON, because plain stdout from UserPromptSubmit would be added to the model's context.
  • Agent modes fail loudly: note and path exit non-zero with a one-line reason when the session id is unset, activation finds no cdocs/_chat/, jq is missing, --as is rejected, or the write fails.
  • One append path. Every write is one printf >> of a whole block, so concurrent writes normally interleave by block; concurrent writers to one record are rare. Agents read records and never edit them. No state exists beyond the record itself.
  • No settings edits. /cdocs:init touches no permissions. Under skip-permissions nothing is needed; in default mode the README says to allow Bash(chat-record:*), since an unallowed note prompts every turn and is denied headless. Running --plugin-dir beside the installed plugin doubles every hook write, so disable one.

5Top-level only

The record belongs to the top-level session. Hook mode is guarded by agent_id, but inside a subagent CLAUDE_CODE_SESSION_ID is the parent's id and nothing in the environment tells the two apart, so a subagent's note would land in the parent's record and could satisfy the parent's Stop check.

The guard is one sentence that opens the per-turn rule in Pillar 2, so it sits beside the instruction it limits and also reaches forks. No agent definition, skill or template carries chat-record text at all; the devlog skill only names the chat_record: field and points to Pillar 2, because dispatched implementers read that skill.

Claude Code top-level session only: chat-record exists nowhere else, and if you were dispatched by the Agent tool (including as a fork), never run it.

In the top-level session, whether or not you are overseeing a loop, before ending a turn that began with a human prompt, append at least one gist bullet with chat-record note (quoted heredoc form), issued in the same parallel tool batch as the turn's last action when the outcome is known.

Other turns (a background agent finishing) may note when they change the state of play; Stop does not require it.

  • Fallback: a scoped PreToolUse deny. A hook with "if": "Bash(chat-record:*)" runs only on chat-record calls and sees agent_id. It ships only if the Phase-1b subagent or fork test shows a leak.
  • Tiered or per-workstream records, including attributed subagent notes, are scoped in cdocs/proposals/2026-10-05-tiered-chat-records-rfp.md.

6Resumption guidance

Compaction happens when you run /compact or the harness auto-compacts. The design does not schedule, request or anticipate it, and no agent tracks its own context. The guidance for what to do afterwards sits in Pillar 2 of orchestration-discipline.md, which /cdocs:init writes into .claude/rules/cdocs.md and which re-injects after every compaction.

  1. First turn a session works on a devlog: run chat-record path and append the result to the devlog's chat_record: list if absent.
  2. At each handoff: refresh the Scratchpoint, and commit devlog and record by explicit path.
  3. After a compaction: run chat-record path; read the Scratchpoint and latest handoff of each devlog that lists that path, newest Scratchpoint first, then the record's last 80 lines (tail -n 80, read further back only if one long paste fills them). Don't rebuild state from the summary. If no devlog lists the path, the record tail is the session's whole durable state.
EventSession idRecordResumption
/compact, auto-compactionkeptsame filestep 3
--resume, --continuekeptsame filethe conversation continues
/clear, --fork-sessionnewnew file; the old one ends at its last sign-offnone: a fresh start carries nothing over

To continue a devlog after /clear, name it; step 1 adds the new record to its chat_record: list. Compaction then becomes a trimming event: the summary's quality no longer decides how well the next window resumes.

Compaction text removed from cdocs

Phase 1a deletes the existing instructions that had agents compact on a schedule or estimate their own context, and keeps every durable-state write at its task-unit boundary so a compaction you run, or the harness runs, loses nothing.

  • Pillar 2's "Proactive compaction cadence": the /compact//clear instruction, the 3-to-5-iteration trigger and the ~150K target. "Handoff-before-compact" becomes "Handoff", written at each task-unit boundary.
  • The loop skills' "then compact" steps in iterate, oversee, propose-revise, full-send and ablate, plus the "~150K-token budget" in oversee's concurrency cap and oversee-arc.md's "own context budget".
  • The overseer_ctx_est column in the iterate devlog. The judge's overseer_thinness reads the inline_work column alone: bloat_detected on a run of inline-work turns, signal_missing when the column is absent.

7Scratchpoint

One ## Scratchpoint section, written only by the devlog's owner and replaced in place on every state-changing turn. Aim for at most about 15 lines and 8 files: entries, moving anything older into a handoff; the agent judges what current state needs. The record accumulates; the Scratchpoint is overwritten. A reader after a compaction takes the Scratchpoint first and the record's tail second.

## Scratchpoint - as_of: 2026-09-22T18:40:11-07:00 - now: wiring the Stop check; block reason text not final - since_handoff: Stop decides from the record's last marker line alone - open: interrupt behavior of Stop - next: run interactive canary, then commit hooks.json entry - files: - plugins/cdocs/hooks/hooks.json (rw): the two shell-hook entries are the template - plugins/cdocs/hooks/validate-cdocs-edit-path.sh (r): jq stdin-parse and silent-exit guards
  • Writers: any agent that owns its devlog: the overseer of iterate, propose-revise, full-send or oversee, a top-level implement or plain session, or a durable specialist with its own devlog. An agent writing into another agent's devlog keeps none; the iterate implementer writes only its Changes Made and Implementer Notes, and its return summary is its checkpoint.
  • files: one line per file read in full or edited since the last handoff, with what it was useful for. It tells a successor whether it needs the bytes; it doesn't make re-reads cheaper. It rolls into the handoff and restarts empty.
  • Not a judge input. The judge reads overseer thinness from the Iteration Log's inline_work column alone; the Scratchpoint is for resumption.

8Devlog splitting

Size (about 12KB or 5 loop rounds) prompts a look for a boundary; it never chooses the cut. A concern is closed when it has its own heading, no open todo in the latest handoff, and feeds no live table in the root. No closed concern means no split.
