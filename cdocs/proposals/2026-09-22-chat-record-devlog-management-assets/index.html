Chat Record, Scratchpoint & Devlog Splitting

How the accepted proposal actually works: the chat-record content model, file layout, hook timing, the Scratchpoint's shape, the devlog-splitting rule, the phase/tiering plan, and the unbuilt per-workstream sketch. Every diagram cites the source it was drawn from.

Two layers, one job each. A hook-written chat record captures every user turn and every compaction summary verbatim at zero LLM cost, plus a sparse, judgment-authored gist entry on the rare turn where the agent decides something is worth a successor knowing — never a reply, never an action log. An agent-written Scratchpoint in the devlog captures dense working state every turn, including a one-line gist per file touched. Delivery across compaction is /compact <steering> first, hooks second.

A Phase-0 canary (eight sandboxed runs) confirmed every hook this design needs fires on Claude Code 2.1.280 headless — including PostCompact, which the original research assumed did not exist. The system makes the compaction summary's quality irrelevant to resumption and compaction rare; it does not, and cannot, prevent native auto-compaction outright.

1File layout

Three artifacts, three writers, three cadences — the whole design is downstream of keeping them separate. There is no separate evidence namespace: raw reproducible proof lives in the devlog's own ## Verification section (a convention that predates this proposal) and, if it outgrows the root, splits as an ordinary -<concern> chunk like anything else — a _verify/ directory was tried during review and removed as scope creep against this proposal's own job, which is chunking devlogs, not inventing a second devlog-adjacent genre.

2Chat-record content: a judgment-driven gist, not a log

This is the part the design got wrong twice before landing. An entry is written only when the agent, at the end of a turn, judges that a future reader would be materially worse off not knowing something — a useful retrieval query, a high-salience file, an opened follow-up. Most turns write nothing, and that silence is the correct, expected output, not a gap to fill. Routine actions (commits, ordinary edits, test runs, dispatches), reasoning, tool output, and the user-facing reply are never captured this way — those are what git and the devlog already record, or the re-readable bulk compaction should drop.

How the content model converged

Round 1

Hook-captured verbatim: every agent turn's last_assistant_message, written automatically by Stop. Rejected — still a reply dump, just bounded to the final text block.

Round 3

Agent-written, but mechanical: one bullet per action item (- <verb> <object>), including routine actions like commits. Rejected — "bullet point" was directional, not a per-action mandate.

Round 4 — final

Agent-written, judgment-driven gist: 0–3 terse notes only when something is genuinely worth knowing, in three named categories. Silence is the expected default.

4Scratchpoint

One ## Scratchpoint section, replaced in place every state-changing turn — never appended, so it cannot become a second chronology competing with the chat record.

cdocs/proposals/2026-09-22-chat-record-devlog-management.md § Scratchpoint · Design Decision 5

Capture vs. delivery — two jobs, not one

Capture

Chat record (hook, verbatim user turns and compaction; sparse agent gist entries) + Scratchpoint (agent, dense state). Makes durable state exist that is at most one turn stale.

Delivery

/compact <steering> primary; PreCompact / SessionStart(compact) / PostCompact hooks secondary. Gets that state read instead of an opaque summary.

Neither alone is enough

Capture without delivery: wrapping still seeds from a devlog up to a task-unit stale. Delivery without capture: nothing better than the devlog exists to read.

Does this obviate native auto-compaction? No. An agent cannot invoke /compact (#71803 open) or prevent it — in AFK/headless runs nobody types anything, so auto-compaction is the only trimming mechanism there (Phase-0 run 3 fired it four times in three minutes under a 100K window). What changes: with a Scratchpoint at most one turn stale plus a reseed pointer, compaction becomes a mechanical trim whose summary quality no longer determines resumption quality. Durable specialists (Pillar 3) are the one true exception — their cap-and-reseed (Phase 3) is a dispatch-level primitive the overseer fully controls, no compaction primitive involved.

5Devlog splitting (rotation)

The trigger to look for a split is size (~12KB or ~5 rounds); the trigger to cut is never size — only a closed concern. A concern is closed when all three hold: it has its own heading; every Open Todo naming it is done or moved to the root's current handoff; no live table still receives rows for it. A landed verification campaign counts as a closed concern like any other.
