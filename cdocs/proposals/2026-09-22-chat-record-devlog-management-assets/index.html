Chat Record, Scratchpoint & Devlog Splitting

How the accepted design works: what one turn writes, the record format, the script and its two hooks, how the record stays top-level only, where compaction guidance lives, the Scratchpoint, the split rule, and the phase plan.

Three artifacts, each with one job. A per-session chat record holds your prompts verbatim and at least one short gist bullet from the agent per turn, each turn closed by a -- <session> at <time> sign-off. A Scratchpoint in the devlog holds current state, replaced in place. Devlog chunks split a long devlog where a concern has closed.

The mechanism is small: two hooks (UserPromptSubmit, Stop), one script on the agent's PATH (chat-record), one permission rule written by /cdocs:init. The record knows nothing about compaction; what to do around a compaction is rule text that re-injects after one.

The record path comes from the session id: the hooks read it from their payload, and the agent's Bash has it as CLAUDE_CODE_SESSION_ID. The file is found by the glob cdocs/_chat/*-<session_id>.md, so --resume on a later day appends to the same file. The devlog links to its record from a two-line ## Chat Record section that the agent fills on its first turn with chat-record path. Records are committed by explicit path in the devlog bookkeeping commit; dispatched agents never stage cdocs/_chat/.

2One turn

Every turn writes your prompt, at least one agent bullet, and a sign-off. The Stop hook only checks that a bullet exists for this turn's prompt id; it never reads or judges content. If the bullet is missing it blocks once, and the second Stop always lets the turn end.

3Record format

A record is a sequence of blocks. Only real speakers get an @ header; the hook is not a speaker, so the turn's end time is a sign-off line after the agent's block rather than a block of its own.

@user: 2026-10-05T12:50:03-07:00 p=3f9a0c1e @end lines should be `-- $session_name at $timestamp` lines to serve more as postscripts @opus-5-5: 2026-10-05T12:51:20-07:00 p=3f9a0c1e - gist: sign-off replaces the @end block; steer sent to the round-7 proposer mid-round -- clauth-opt-context at 2026-10-05T12:51:24-07:00 @harness: 2026-10-05T13:00:41-07:00 p=7c2e55d0 <task-notification> ... Agent "Revise chat-record proposal r7" finished ... @opus-5-5: 2026-10-05T13:02:10-07:00 p=7c2e55d0 - gist: r7 committed (62febaa); no env var separates subagent Bash, so the guard is rule text - follow-up: whether a mid-turn prompt fires UserPromptSubmit; interactive check (e) -- clauth-opt-context at 2026-10-05T13:02:15-07:00

illustrative excerpt in the proposal's grammar, built from this arc's own turns

  • hook@user / @harnesswritten by UserPromptSubmit at submission time, prompt verbatim. A prompt whose first token is a harness tag such as <task-notification is @harness; it owes a bullet like any other turn.
  • agent@<model-short>written by chat-record note --as <model-short>; the script adds the timestamp and the p= that ties the entry to its prompt. Without --as the speaker is assistant.
  • hook-- <session> at <ts>written by Stop. The session token is the /rename title from the transcript, mapped to [A-Za-z0-9._-], else the first 8 hex of the session id. A turn's duration is its @user time to its sign-off.
PatternRegex
header^@[A-Za-z0-9][A-Za-z0-9._-]*: then <timestamp> and optional p=<pid8>
sign-off^-- [A-Za-z0-9._-]+ at <ISO-8601 with offset>( p=[0-9a-f]{8})?$
bodyany line matching neither; a body line that looks like either gets one leading backslash, stripped on read

The optional p= on a sign-off is written only if prompts typed mid-turn turn out to fire UserPromptSubmit before the turn's Stop; readers then match by p= instead of position.

Gist bullets

One to three bullets per turn, one line each, under about 120 characters. The test for a bullet: would a successor reading only the prompts and these bullets know where things stand?

gist: (default)

what the turn concluded, decided or changed

query:

a search that proved useful and what it found

read:

a high-salience file and why it mattered

follow-up:

an open thread to come back to

This is a guideline, not a prohibition list. Don't log every commit, test run, edit or tool output, and don't paste the reply. A commit that closes a long thread, or a test result that changes the plan, can be the turn's gist. The shape to avoid is the enumerated log (- edited X - ran tests - committed abc); the shape to produce is the one-line state of play.

4The script and its hooks

plugins/cdocs/bin/chat-record is Bash plus jq. A plugin's bin/ is on the Bash tool's PATH while the plugin is enabled, so the agent runs it as a bare command.

ModeInvocationBehavior
hookchat-record UserPromptSubmitappend @user or @harness with p=; never blocks
hookchat-record Stopsign-off, or block once (table below)
agentchat-record note [--as m] [--p pid8], bullets on stdinappend an entry; p= from --p, else the last prompt header
agentchat-record pathprint the record path; never creates the file

The note body comes only from stdin, written as a quoted heredoc, which does no shell expansion. A double-quoted argument would execute backticks and $(...), and a single-quoted one breaks on apostrophes.

chat-record note --as opus-5-5 <<'EOF' - query: `rg -n "prompt_id"` found the Stop/UserPromptSubmit correlation EOF
Stop seesWritesEmits
an agent entry with this turn's p=, or stop_hook_activesign-offnothing
no entry, block allowednothingdecision: block with the real path and the exact note command
no entry, block suppressed (interrupted turn, or no prompt_id)sign-offnothing
  • Hook mode exits silently (exit 0, no write, no block) when the payload carries agent_id, CDOCS_CHAT_RECORD=off, jq is missing, there is no cdocs/ above the working directory, or (for Stop) no record exists.
  • Agent modes fail loudly: note and path exit non-zero with a one-line reason when the session id is unset, no cdocs/ is found, or the write fails.
  • One append path. Every write is one printf >> of a whole block, so racing writes interleave by block. Agents read records and never edit them. No runtime state files exist.
  • Permissions. /cdocs:init merges "Bash(chat-record:*)" into permissions.allow; without it the per-turn call prompts interactively and is denied headless.

5Top-level only

The record belongs to the top-level session. Inside a subagent, CLAUDE_CODE_SESSION_ID is the parent's id and nothing in the environment tells the two apart, so a subagent's note would land in the parent's record and could satisfy the parent's Stop check.

  • Guard: rule text. The per-turn rule opens "Top-level session only: if you were dispatched by the Agent tool (including as a fork), never run chat-record", and each cdocs agent definition carries the same line. An agent knows whether it was dispatched.
  • Fallback: a scoped PreToolUse deny. A hook with "if": "Bash(chat-record:*)" runs only on chat-record calls and sees agent_id. It ships if the Phase-1 subagent or fork test shows a leak.
  • Tiered or per-workstream records, including attributed subagent notes, are scoped in cdocs/proposals/2026-10-05-tiered-chat-records-rfp.md.

6Compaction guidance lives in rules

The record has no compaction hook and no session or compaction lines. Compaction is a user action, so the guidance sits in Pillar 2 of orchestration-discipline.md, which /cdocs:init writes into .claude/rules/cdocs.md and which re-injects after every compaction.

  1. First turn of a session: run chat-record path and write the result into the devlog's ## Chat Record section.
  2. At a task-unit boundary: write the handoff, refresh the Scratchpoint, commit devlog and record by path, then ask the user to run /clear or a steered /compact Preserve verbatim from cdocs/devlogs/<devlog>.md: the ## Scratchpoint block and the latest handoff…
  3. After any compaction or clear: run chat-record path; read the Scratchpoint and latest handoff of the devlog that names that path, then the last five blocks of the record. Don't rebuild state from the summary.

This does not stop auto-compaction in headless or AFK sessions. It makes the summary's quality irrelevant to how well the next window resumes.

7Scratchpoint

One ## Scratchpoint section, replaced in place on every state-changing turn: at most 15 lines and 8 files: entries. The record accumulates; the Scratchpoint is overwritten. A reader after a compaction takes the Scratchpoint first and the record's tail second.

## Scratchpoint - as_of: 2026-09-22T18:40:11-07:00 ctx: ~140K (10% inline) - now: wiring the Stop check; block reason text not final - since_handoff: Stop.prompt_id matches UserPromptSubmit.prompt_id - open: interrupt behavior of Stop; /clear effect on session_id - next: run interactive canary, then commit hooks.json entry - files: - plugins/cdocs/hooks/hooks.json (rw): the two shell-hook entries are the template - plugins/cdocs/hooks/validate-cdocs-edit-path.sh (r): jq stdin-parse and silent-exit guards
  • Writers: the overseer of any loop and any durable specialist. One-shot legs don't keep one; their return summary is their checkpoint.
  • files: one line per file read in full or edited since the last handoff, with what it was useful for. It tells a successor whether it needs the bytes; it doesn't make re-reads cheaper. It rolls into the handoff and restarts empty.
  • Judge signal: a Scratchpoint whose as_of is older than two Iteration Log rows, or missing, is reported as the existing overseer_thinness: signal_missing.

8Devlog splitting

Size (about 12KB or 5 loop rounds) prompts a look for a boundary; it never chooses the cut. A concern is closed when it has its own heading, no open todo in the latest handoff, and feeds no live table in the root. No closed concern means no split.
