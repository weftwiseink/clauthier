Chat Record, Scratchpoint & Devlog Splitting

How the accepted proposal actually works: file layout, hook timing, the Scratchpoint's shape, the devlog-splitting rule, the phase/tiering plan, and the unbuilt per-workstream sketch. Every diagram cites the source it was drawn from.

Two layers, one job each. A hook-written chat record captures every user turn, assistant reply, and compaction summary verbatim at zero LLM cost. An agent-written Scratchpoint in the devlog captures dense working state every turn, including a one-line gist per file touched. Delivery across compaction is /compact <steering> first, hooks second.

A Phase-0 canary (seven sandboxed runs) confirmed every hook this design needs fires on Claude Code 2.1.280 headless — including PostCompact, which the original research assumed did not exist. The system makes the compaction summary's quality irrelevant to resumption and compaction rare; it does not, and cannot, prevent native auto-compaction outright.

3Scratchpoint

One ## Scratchpoint section, replaced in place every state-changing turn — never appended, so it cannot become a second chronology competing with the chat record.

cdocs/proposals/2026-09-22-chat-record-devlog-management.md § Scratchpoint · Design Decision 5

Capture vs. delivery — two jobs, not one

Capture

Chat record (hook, verbatim) + Scratchpoint (agent, dense state). Makes durable state exist that is at most one turn stale.

Delivery

/compact <steering> primary; PreCompact / SessionStart(compact) / PostCompact hooks secondary. Gets that state read instead of an opaque summary.

Neither alone is enough

Capture without delivery: wrapping still seeds from a devlog up to a task-unit stale. Delivery without capture: nothing better than the devlog exists to read.

Does this obviate native auto-compaction? No. An agent cannot invoke /compact (#71803 open) or prevent it — in AFK/headless runs nobody types anything, so auto-compaction is the only trimming mechanism there (Phase-0 run 3 fired it four times in three minutes under a 100K window). What changes: with a Scratchpoint at most one turn stale plus a reseed pointer, compaction becomes a mechanical trim whose summary quality no longer determines resumption quality. Durable specialists (Pillar 3) are the one true exception — their cap-and-reseed (Phase 3) is a dispatch-level primitive the overseer fully controls, no compaction primitive involved.

4Devlog splitting (rotation)

The trigger to look for a split is size (~12KB or ~5 rounds); the trigger to cut is never size — only a closed concern. A concern is closed when all three hold: it has its own heading; every Open Todo naming it is done or moved to the root's current handoff; no live table still receives rows for it.
