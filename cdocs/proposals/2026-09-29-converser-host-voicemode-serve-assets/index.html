Converser Design Map

BLUF

Audio moves to the host. Each container project gets its own loopback voicemode serve process under systemd --user, with its own bearer token and only the converse tool. The container reaches it through one --network pasta:-T,<port> forward. The host side is converser-host, a shell CLI plus three unit files. It wraps VoiceMode's unsafe host defaults: wildcard binds, the token on argv, and auto-enabled units. Inside the container, the converser is an ordinary claude session started by a launcher. Claude Code itself is the MCP HTTP client; no daemon runs in the container. All new code goes in the clauthier converser plugin directory. Weftwise gets one uncommitted line, and lace is not changed.

Question 1 · Components

Host, forward, container

The host runs everything that touches audio. The container runs claude sessions and nothing else new. Two channels cross the boundary. The first is an HTTP MCP connection through the pasta forward, carried on every call. The second is a one-shot stdin handoff of the token and port when the container is created.

Question 1 · The token

What in the container receives the token?

Answer

A file, then a launcher, then Claude Code. There is no client daemon. converser-host instance handoff pipes the token and port over stdin (podman exec -i) into ~/.config/converser/token and ~/.config/converser/port in the container user's home (0600). When the user runs the converser launcher, it reads both files once. It uses the shell's builtin printf to write a temporary 0600 MCP config under $XDG_RUNTIME_DIR, then execs claude --strict-mcp-config --mcp-config <that file>. From then on, the converser's own Claude Code process is the MCP HTTP client. It sends Authorization: Bearer <token> on every request through the pasta forward.

Question 1 · Behavior

A spoken request, the turn-end summary, and a redirected question

The converser does two jobs. It relays user speech outward as SendMessage, and it speaks what comes back from overseer turn ends. Relays go out first and are read back after. The only question asked before sending checks intent. Agent text is never forwarded to another agent.

Bounds that make the 600 s client timeout safecall shape

Claude Code's HTTP MCP request timer defaults to 60 s. VoiceMode's default listen_duration_max is 120 s with no server-side clamp, so without a per-server timeout every default listen aborts client-side at 60 s. That abort is the #522 trigger. The converser's security floor bounds each call:

  • listen_duration_max ≤ 90, single-turn (no turns), spoken messages under a minute.
  • wait_for_conch only true or false. A number would replace VOICEMODE_CONCH_TIMEOUT=60. No hold_conch, and never conch_mode=callback.
  • Worst case: about 60 s conch wait + 60 s playback + 90 s listen + a few seconds of STT. That is well under 600 s.
  • These are prompt-level bounds. They bind the converser, not another container process that holds the token.

Gate p: a 90 s listen survives with the field and aborts near 60 s without it.

Why enablement cannot be plugin-scopedthe managed-file argument
  • A plugin's hooks fire wherever the plugin is enabled, and enablement is per settings file.
  • User scope is ~/.claude/settings.json, the bind mount shared by the host and every container, so hooks would run everywhere.
  • Project scope would run for every session in the repo, host-side too, and for collaborators. It also outranks user scope for enabledPlugins. So the plugin must never appear in any project settings file.
  • Only /etc/claude-code/managed-settings.d/50-converser.json inside the container scopes and force-enables it. In stage 3 it carries extraKnownMarketplaces.clauthier (directory source /var/home/mjr/code/weft/clauthier/main) and enabledPlugins: {"converser@clauthier": true}.

  • crossSessionInbound: "accept" and the VoiceMode MCP entry cannot come from a plugin. They go through the launcher's --settings and --mcp-config.
Question 3 · Interaction model

Relay first, verify intent by exception, correct by number

Rules

  • Relay cleaned speech. Drop disfluencies, false starts, and obvious transcription slips. Keep the user's words, emphasis, hedges, and uncertainty. Never upgrade "maybe look at" into "fix".
  • Send, then read back. The readback says what was actually sent. The control channel stops playback, not a send, so reading back first would buy nothing. The raw transcript is never echoed for confirmation.
  • Confirm only to verify intent, for three reasons. Comprehension: the target is unclear, or a key detail came through low-confidence. Sensibility: the request is self-contradictory or makes no sense against the target's work. Destructive intent: a truly destructive action the user did not signal explicitly. Keep it short: "Weftwise or lace?"
  • Labelled history on one global sequence. Entries read #4: weftwise-overseer → …. The label is the target's session name as ListAgents shows it (--name or /rename). An unnamed session gets an inferred label, stated on first use.
  • Correct by follow-on. "Fix four" sends a correction to the same target, citing #4. Delivered messages are never retracted.
  • Human prose both ways. To agents: ordinary sentences, opening with a voice-relay marker. To the user: short spoken sentences, with the rest left in the history.
  • Structural relay rule. Only user speech is forwarded. Stop-post text is spoken or summarized, never passed to another overseer.
  • Listen gating. The mic opens only when the user starts an exchange, or right after the converser asked something. There is no idle open-mic loop. A headset is the default.

The session names and message text are invented. Every target must be a session in the same container, since container and host sessions cannot message each other. The format follows the proposal: number first, one global sequence, → for relays, ← for spoken inbound. In v0 the history is the converser's own terminal transcript. A persistent ledger would be a stage-3 fixed-path converser-io MCP tool, never Write.

Accepted risk · the audio stream is a keyboard

Anything captured inside an open listen window is treated as the user's input, just like keystrokes in the converser terminal. There is no speaker attribution. A video, a call, another person, or leaked TTS inside an open window is indistinguishable from the user, and a bypass overseer approves everything. Intent verification is a comprehension aid, not a control. What keeps the "keyboard" physically scoped: listen gating, the headset default, the visible numbered history (after the fact), and the voice marker (advisory). This fits a one-user, desk-bound, headset-first prototype. Hands-free use in a shared room stays an explicit opt-in.

Question 1 · Lifecycle

Install order, and what a rebuild erases

The host install order matters for security. The firewall goes up before anything can bind. Installers run with --no-auto-enable. Upstream units are removed, reloaded, and masked before the package's own units start. The container half is the fragile half: every recreate erases what stage 1 hand-placed.

Question 4 · Security posture

Threat, control, residual

Moving audio to the host removes four threats: pulse-socket mic and monitor capture, pulse module loading, inode pinning, and double capture per container. It adds a network-reachable token. The host process scopes the tools, because any container process that holds the token can speak raw JSON-RPC.

Review notes

Where the proposal leaves a connection underspecified

None of these blocks stage 1. Each is a place where a diagram above had to infer or leave an edge unlabelled. Gates e, f, j, and k are where most of them get settled.

  • How does the Stop hook find the converser?Specified: the converser's --settings SessionStart hook records its inbox path at /run/user/1000/converser.sockpath, and the hooks post there. The round-1 review verified that $CLAUDE_CODE_MESSAGING_SOCKET is exported before SessionStart. The proposal does not name the variable. It also does not say whether the sockpath file is removed on exit, so a stale file is left for the "socket answers" liveness check to catch.
  • How does the converser learn session names?From ListAgents, which only covers sessions in its own container, because container and host sessions cannot message each other. The inferred label for unnamed sessions (lace-main (unnamed)) assumes ListAgents exposes a working directory. The proposal does not verify that, and the label rule is prompt-level.
  • Where does the Stop hook get its own name for From:?Test Plan item 9 says "registry-resolved From:", but the proposal never defines the registry. The converser needs this name to label inbound entries (#5: weftwise-overseer ←).
  • What is the raw inbox wire format?It is pinned empirically by gate f (a python3 socket script), not specified. Stage-1 hook bodies are "inline in the managed file", and whether "condensed" means truncation by the hook or summarization is left open.
  • How does a redirected overseer address the converser?Implied by --name converser plus ListAgents. The deny reason's exact wording, and whether it names the session, are unspecified.
  • Where does the port come from at launch?From the handed-off port file. The runArgs line is a separate copy of the same number. The proposal names no check that the two agree after an instance add --port change.
